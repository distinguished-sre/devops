## Зачем это нужно

Контейнер одноразовый: удалили и создали заново, а всё, что он записал внутрь себя, исчезло. Заметки пользователей терять нельзя, поэтому данные выносят в том (volume). Второй вопрос: как один контейнер находит другой. IP-адреса меняются при каждом пересоздании, поэтому контейнеры общаются по имени в пользовательской сети (user-defined network). На работе это самая частая причина двух аварий: «после деплоя пропали данные» и «сервис не видит базу».

Шаг проекта: «Заметки» пишут данные в именованный том `notes-data`, смонтированный в `/data`, а контейнеры живут в сети `notes-net`.

## Теория

### Где живут данные контейнера

Образ состоит из слоёв только для чтения. Поверх них при запуске добавляется один тонкий слой для записи (writable layer). Всё, что процесс пишет в файловую систему без тома, попадает туда. Пока контейнер существует, файлы на месте: `docker stop` и `docker start` их не трогают. Команда `docker rm` удаляет контейнер вместе со слоем, и данные пропадают безвозвратно.

Есть три способа подключить хранилище снаружи:

| Способ | Кто управляет | Где лежит | Для чего |
|---|---|---|---|
| Именованный том (named volume) | Docker | `/var/lib/docker/volumes/<имя>/_data` | данные приложений и баз |
| Bind mount | ты | любой каталог хоста | код при разработке, конфиги |
| tmpfs | ядро | только оперативная память | временное и секретное, исчезает при остановке |

> **Проверь понимание:** контейнер с «Заметками» записал файл в `/data` без тома. Ты сделал `docker stop`, потом `docker start`. Данные на месте? А после `docker rm` и нового `docker run`?

<details markdown="1">
<summary>Ответ</summary>

После `stop` и `start` данные на месте: контейнер и его слой записи живы. После `rm` слой удалён, новый контейнер стартует с чистым `/data` из образа. Если в 4.2 образ объявляет `VOLUME /data`, Docker создаст анонимный том, и старые данные останутся в нём, но найти его по имени трудно. Поэтому том всегда называют явно.

</details>

### Именованный том и bind mount

Именованный том создаётся командой `docker volume create` или автоматически при первом `-v имя:путь`. Если в образе по пути монтирования уже есть файлы, Docker копирует их в пустой новый том вместе с владельцем. Так том получает права пользователя из образа (uid 10001).

Bind mount (`-v /путь/на/хосте:/путь/в/контейнере`) подключает существующий каталог хоста как есть. Docker ничего не копирует и не меняет владельца. Если каталог принадлежит root, а процесс в контейнере работает под uid 10001, запись даст `Permission denied`. Это ровно то же правило прав из [урока 1.3](../01-linux/03-users-permissions.md): ядро сверяет числовой uid, имена пользователей внутри контейнера и на хосте не связаны.

Два синтаксиса: короткий `-v` и явный `--mount type=volume,source=notes-data,target=/data`. Разница в поведении: при `-v` с несуществующим каталогом хоста Docker молча создаст его (от root), а `--mount type=bind` с отсутствующим путём завершится ошибкой. Для bind mount в скриптах лучше `--mount`: опечатка в пути не создаст пустой каталог.

> **Проверь понимание:** почему bind mount на каталог, созданный командой `mkdir data`, часто даёт `Permission denied`, а именованный том нет?

<details markdown="1">
<summary>Ответ</summary>

Каталог `data` принадлежит твоему пользователю (uid 1000 или подобный), а процесс в контейнере работает под uid 10001, для него это чужой каталог. Именованный том при первом создании копирует содержимое и владельца из образа, где `/data` уже принадлежит 10001. Чинится `sudo chown 10001:10001 data`.

</details>

### Сети Docker и DNS по имени

Каждый контейнер получает свой сетевой стек (network namespace, [урок 4.1](01-containers-idea.md)). По умолчанию он подключён к сети `bridge` (мост docker0). У неё два свойства, о которые спотыкаются:

- в сети `bridge` по умолчанию нет DNS по именам контейнеров, доступны только IP;
- порт контейнера снаружи недоступен, пока его не опубликовали флагом `-p хост:контейнер`.

Пользовательская сеть (`docker network create notes-net`) решает первое: встроенный DNS-сервер Docker (адрес 127.0.0.11 внутри контейнера) отвечает на имя контейнера его текущим IP. Контейнер `notes` в сети `notes-net` виден другим участникам сети как `notes`, а порт 8080 доступен им без всякого `-p`. `-p` нужен только для доступа с хоста и снаружи.

Отсюда важное различие: `EXPOSE 8080` в Dockerfile только документация, порт он не открывает. Открывает `-p 127.0.0.1:8080:8080`. Слушать при этом приложение обязано на `0.0.0.0` (это `HOST=0.0.0.0` из 4.2), иначе мост его не достанет.

Сеть `host` (`--network host`) убирает изоляцию: контейнер использует сетевой стек хоста, публикация портов не нужна и не работает. Для «Заметок» она не нужна, знать её надо для собеседования.

> **Проверь понимание:** почему на IP-адрес контейнера в конфигах полагаться нельзя?

<details markdown="1">
<summary>Ответ</summary>

IP выдаётся из пула сети при старте и меняется при каждом пересоздании контейнера. Имя стабильно, DNS Docker всегда отвечает актуальным адресом. Тот же принцип в Kubernetes: обращаются к имени Service, а не к IP пода.

</details>

### Задание 1. Данные без тома пропадают при rm

**Цель:** своими руками увидеть, что данные живут в слое контейнера.

**Предскажи:** ты запишешь заметку, остановишь и снова запустишь контейнер, потом удалишь его и создашь новый с тем же образом. В каких двух случаях заметка будет на месте?

<details markdown="1">
<summary>Ответ</summary>

Заметка сохранится после `stop` и `start` и пропадёт после `rm` и нового `run`.

</details>

**Шаги:**

1. Запусти контейнер без тома и добавь заметку:

```bash
docker run -d --name notes-tmp -p 127.0.0.1:8080:8080 notes:0.3.0
curl -s -X POST -d 'заметка без тома' http://127.0.0.1:8080/notes
curl -s http://127.0.0.1:8080/notes
```

2. Перезапусти контейнер и проверь:

```bash
docker stop notes-tmp && docker start notes-tmp
sleep 1
curl -s http://127.0.0.1:8080/notes
```

3. Удали контейнер и создай новый:

```bash
docker rm -f notes-tmp
docker run -d --name notes-tmp -p 127.0.0.1:8080:8080 notes:0.3.0
sleep 1
curl -s http://127.0.0.1:8080/notes
docker rm -f notes-tmp
```

**Что должно получиться:**

```text
заметка без тома
```

После перезапуска заметка на месте, после пересоздания вывод пустой.

**Объясни себе:**

- Где физически лежала заметка между шагами 1 и 2?
- Почему `docker rm -f` уничтожил её, хотя файл был записан на диск?

**Типичные ошибки:**

- `docker: Error response from daemon: Conflict. The container name "/notes-tmp" is already in use`: имя занято старым контейнером. Удали его: `docker rm -f notes-tmp`.
- `Bind for 127.0.0.1:8080 failed: port is already allocated`: порт держит другой контейнер или хост-сервис. Найди: `sudo ss -tulpn | grep 8080`.

### Задание 2. Именованный том сохраняет данные

**Цель:** вынести `/data` в том `notes-data` и пережить удаление контейнера.

**Предскажи:** том создан заранее и пуст. Кто будет владельцем каталога `/data` внутри контейнера и получится ли записать заметку?

<details markdown="1">
<summary>Ответ</summary>

Docker при первом монтировании копирует в пустой том содержимое и владельца каталога `/data` из образа. Владелец 10001, запись пройдёт.

</details>

**Шаги:**

```bash
# создаём том и смотрим, где он лежит
docker volume create notes-data
docker volume inspect notes-data

# запускаем «Заметки» с томом и пишем заметку
docker run -d --name notes -p 127.0.0.1:8080:8080 -v notes-data:/data notes:0.3.0
sleep 1
curl -s -X POST -d 'заметка в томе' http://127.0.0.1:8080/notes

# проверяем владельца каталога внутри контейнера
docker exec notes ls -ld /data

# убиваем контейнер и поднимаем новый с тем же томом
docker rm -f notes
docker run -d --name notes -p 127.0.0.1:8080:8080 -v notes-data:/data notes:0.3.0
sleep 1
curl -s http://127.0.0.1:8080/notes
```

**Что должно получиться:**

```text
[
    {
        "Name": "notes-data",
        "Driver": "local",
        "Mountpoint": "/var/lib/docker/volumes/notes-data/_data",
        "Scope": "local"
    }
]
drwxr-xr-x 2 10001 10001 4096 Sep 29 10:00 /data
заметка в томе
```

Поля вывода `volume inspect` (дата, метки) у тебя могут отличаться. Главное: после пересоздания контейнера заметка на месте.

**Объясни себе:**

- Что именно пережило `docker rm`: контейнер, образ или том?
- Что случится, если запустить два контейнера с одним томом и писать в один файл?

**Типичные ошибки:**

- `docker: Error response from daemon: Conflict. The container name "/notes" is already in use`: забыл `docker rm -f notes` перед повторным запуском.
- Данные «исчезли» после `docker run`, хотя том был: в `-v` опечатка в имени (`notes_data` вместо `notes-data`), Docker молча создал новый пустой том. Сверься: `docker volume ls`.

### Задание 3. Бэкап и восстановление тома

**Цель:** упаковать том `notes-data` в архив и развернуть его в другой том.

**Предскажи:** в томе `notes-data` одна заметка. Ты сделаешь архив, создашь том `notes-restore` и распакуешь туда. Как проверить, что данные целы, не запуская «Заметки»?

<details markdown="1">
<summary>Ответ</summary>

Смонтировать оба тома в одноразовый контейнер и сравнить `cat` или `sha256sum` файла. Можно и запустить «Заметки» на новом томе и прочитать `GET /notes`.

</details>

**Шаги:**

```bash
mkdir -p ~/notes-backup

# бэкап: том только для чтения, каталог хоста для архива
docker run --rm -v notes-data:/data:ro -v "$HOME/notes-backup":/backup \
  alpine:3.22 tar czf /backup/notes-data.tar.gz -C /data .

# восстановление в новый том
docker volume create notes-restore
docker run --rm -v notes-restore:/data -v "$HOME/notes-backup":/backup \
  alpine:3.22 tar xzf /backup/notes-data.tar.gz -C /data

# сверяем контрольные суммы
docker run --rm -v notes-data:/a:ro -v notes-restore:/b:ro alpine:3.22 \
  sh -c 'sha256sum /a/notes.txt /b/notes.txt'

# запускаем «Заметки» на восстановленном томе
docker run -d --name notes-r -p 127.0.0.1:8080:8080 -v notes-restore:/data notes:0.3.0
sleep 1
curl -s http://127.0.0.1:8080/notes
docker rm -f notes-r
```

**Что должно получиться:**

```text
9c1d...e42a  /a/notes.txt
9c1d...e42a  /b/notes.txt
заметка в томе
```

Суммы одинаковые (хеши у тебя другие, но совпадают между собой).

**Объясни себе:**

- Зачем в бэкапе том смонтирован с `:ro`?
- Почему бэкап файла работающей базы таким способом может оказаться битым? Как это решают для PostgreSQL (см. [урок 4.4](04-sql-postgres-basics.md))?

**Типичные ошибки:**

- `tar: can't open '/backup/notes-data.tar.gz': No such file or directory`: каталог `~/notes-backup` не создан или не смонтирован.
- `Unable to find image 'alpine:3.22' locally` с долгой паузой: обычная загрузка образа, не ошибка.

### Задание 4. Своя сеть и DNS по имени

**Цель:** сравнить `bridge` по умолчанию и пользовательскую сеть.

**Предскажи:** два контейнера в сети `bridge` по умолчанию. Один из них пробует открыть `http://notes:8080`. Что произойдёт? А в сети `notes-net`?

<details markdown="1">
<summary>Ответ</summary>

В default bridge имя не резолвится: `bad address 'notes'`. В `notes-net` встроенный DNS вернёт IP контейнера и запрос пройдёт.

</details>

**Шаги:**

```bash
# 1. default bridge: имя не работает
docker run -d --name notes -v notes-data:/data notes:0.3.0
docker run --rm alpine:3.22 wget -qO- -T 3 http://notes:8080/healthz
docker rm -f notes

# 2. пользовательская сеть: имя работает
docker network create notes-net
docker run -d --name notes --network notes-net -v notes-data:/data notes:0.3.0
docker run --rm --network notes-net alpine:3.22 wget -qO- -T 3 http://notes:8080/healthz

# 3. смотрим IP и почему на него нельзя полагаться
docker inspect notes | jq -r '.[0].NetworkSettings.Networks["notes-net"].IPAddress'
docker restart notes
docker inspect notes | jq -r '.[0].NetworkSettings.Networks["notes-net"].IPAddress'
docker network inspect notes-net | jq -r '.[0].Containers[].Name'
```

**Что должно получиться:**

```text
wget: bad address 'notes'
ok
172.18.0.2
172.18.0.2
notes
```

После `restart` IP часто прежний, но гарантии нет: остановишь два контейнера и запустишь в другом порядке, адреса поменяются местами. Имя работает всегда.

**Объясни себе:**

- Порт 8080 не публикован на хост, а wget его достал. Почему?
- Что изменится, если запустить с `-p 127.0.0.1:8080:8080`?

**Типичные ошибки:**

- `wget: bad address 'notes'`: контейнеры в разных сетях или в default bridge. Проверь `docker network inspect notes-net`.
- `wget: can't connect to remote host (172.18.0.2): Connection refused`: имя нашлось, но приложение слушает `127.0.0.1`. Нужен `HOST=0.0.0.0` (урок 4.2).
- `Error response from daemon: network notes-net already exists`: сеть создана ранее, это нормально.

### Задание 5. Шаг проекта: том и сеть «Заметок»

**Цель:** зафиксировать в проекте запуск «Заметок» с томом `notes-data` и сетью `notes-net`.

**Предскажи:** при запуске из скрипта повторный `docker network create` завершится ошибкой и остановит скрипт с `set -e`. Как сделать создание идемпотентным?

<details markdown="1">
<summary>Ответ</summary>

Проверять существование: `docker network inspect notes-net >/dev/null 2>&1 || docker network create notes-net`. Так скрипт можно запускать сколько угодно раз.

</details>

**Шаги:**

1. Останови старый контейнер:

```bash
docker rm -f notes
```

2. Подготовь сеть и том, если их ещё нет, и запусти сервис на 127.0.0.1 хоста:

```bash
docker network inspect notes-net >/dev/null 2>&1 || docker network create notes-net
docker volume inspect notes-data >/dev/null 2>&1 || docker volume create notes-data
docker run -d --name notes --network notes-net \
  -p 127.0.0.1:8080:8080 -v notes-data:/data \
  --restart unless-stopped notes:0.3.0
```

3. Убедись, что всё работает и данные на месте:

```bash
sleep 1
curl -s http://127.0.0.1:8080/healthz
curl -s http://127.0.0.1:8080/notes
docker volume ls --filter name=notes-data
docker network ls --filter name=notes-net
```

4. Убери за собой учебные объекты:

```bash
docker volume rm notes-restore
rm -rf ~/notes-backup
```

**Что должно получиться:**

```text
ok
заметка в томе
DRIVER    VOLUME NAME
local     notes-data
NETWORK ID     NAME        DRIVER    SCOPE
a1b2c3d4e5f6   notes-net   bridge    local
```

Новых файлов в репозиторий `~/notes` этот шаг не добавляет: меняется состояние Docker (том `notes-data`, сеть `notes-net`). Эталон проекта на конец урока: <https://github.com/distinguished-sre/devops/tree/devops/project/notes>. Ты его продолжишь в [уроке 4.4](04-sql-postgres-basics.md), где в сети `notes-net` появится PostgreSQL.

**Объясни себе:**

- Что случится с заметками при `docker rm -f notes`, а что при `docker volume rm notes-data`?
- Зачем публиковать порт именно на `127.0.0.1`, а не на `0.0.0.0`? (Вспомни [урок 2.7](../02-network/07-firewall.md): Docker обходит ufw.)

**Типичные ошибки:**

- `Error response from daemon: remove notes-data: volume is in use`: том ещё смонтирован в контейнер (даже остановленный). Найди: `docker ps -a --filter volume=notes-data`.
- `Error response from daemon: network notes-net has active endpoints`: к сети подключены контейнеры, сначала удали их.

## Сломай и почини

Сценарии запускает скрипт из эталона. Не читай его: смысл в диагностике.

```bash
cd ~/notes
bash break/4.3/break.sh 1
```

### Симптом

Сценарий 1: после «уборки диска» в сервисе пусто, все заметки пропали, контейнер жив, `/healthz` отвечает `ok`.

Сценарий 2 (`bash break/4.3/break.sh 2`): сервис-клиент получает `Name or service not known` при обращении к `notes`, хотя оба контейнера запущены.

### Гипотезы

Сценарий 1:

1. Кто-то удалил контейнер без тома, а новый смонтировал другой том.
2. Том удалила команда очистки Docker.
3. Приложение пишет не в `/data`.

Сценарий 2:

1. Опечатка в имени.
2. Контейнеры в разных сетях.
3. Клиент в default bridge, где DNS по именам нет.
4. Приложение не слушает нужный интерфейс.

### Проверки

```bash
# сценарий 1: какие тома есть и что к ним подключено
docker volume ls
docker inspect notes | jq '.[0].Mounts'
history | grep -E 'prune|volume rm'

# сценарий 2: в каких сетях контейнеры
docker inspect notes | jq '.[0].NetworkSettings.Networks | keys'
docker inspect <клиент> | jq '.[0].NetworkSettings.Networks | keys'
```

### Исправление

<details markdown="1">
<summary>Разбор сценариев</summary>

**Сценарий 1.** Команда `docker system prune --volumes` удаляет тома, которые не подключены ни к одному контейнеру, и остановленный контейнер в счёт не идёт только пока он существует. Если контейнер был удалён (`rm`), том стал «осиротевшим», и `prune --volumes` его уничтожила. Данные восстанавливаются только из бэкапа задания 3: создай том, распакуй архив, запусти сервис. Профилактика: никогда не запускать `prune --volumes` на проде, делать бэкапы по расписанию (см. [урок 1.7](../01-linux/07-bash-in-ops.md)), для важных томов не удалять контейнер без необходимости, `docker system prune` без `--volumes` тома не трогает.

**Сценарий 2.** Клиент запущен в сети `bridge`, а `notes` в `notes-net`. Решение: подключить клиента ко второй сети или пересоздать в правильной: `docker network connect notes-net <клиент>`, либо `--network notes-net` при запуске. Проверка: `docker exec <клиент> getent hosts notes` должен вернуть IP.

</details>

## Вопросы с собеседований

### 1. [junior] Разработчик удалил контейнер с приложением, и пропали загруженные файлы. Что произошло и как предотвратить?

Файлы лежали в слое записи контейнера, `docker rm` удалил его. Нужно вынести каталог в именованный том или bind mount, а в идеале хранить файлы вне контейнера (объектное хранилище). Сначала проверю `docker inspect` на `Mounts`, чтобы понять, был ли том вообще, и `docker volume ls` на осиротевшие тома.

**Что хотят услышать:** writable layer, `rm` против `stop`, том, поиск потерянного тома, бэкап.

**Красный флаг:** «данные хранятся в контейнере, просто перезапусти».

### 2. [junior] Чем именованный том отличается от bind mount, что выберешь для базы данных?

Именованным томом управляет Docker, он лежит в `/var/lib/docker/volumes`, переносим, права берёт из образа. Bind mount это каталог хоста как есть. Для базы возьму именованный том: нет зависимости от структуры каталогов и владельца на хосте. Bind mount оставлю для конфигов и кода при разработке.

**Что хотят услышать:** переносимость, права, `--mount` строже `-v`.

**Красный флаг:** «это одно и то же, разница в синтаксисе».

### 3. [middle] Диск сервера заполнен, а `du` по обычным каталогам показывает мало. Как найдёшь виновника в Docker?

Смотрю `df -h`, потом `docker system df -v`: размеры образов, контейнеров, томов. Проверяю логи контейнеров в `/var/lib/docker/containers/*/*-json.log` (без ротации они растут бесконечно) и записываемые слои разговорчивых контейнеров. Диск после `docker rm` освобождается не сразу, если файл держит процесс.

**Что хотят услышать:** `docker system df`, json-логи и ротация, тома, `du` под root, `lsof +L1`.

**Красный флаг:** «сделаю `docker system prune -a --volumes`».

### 4. [middle] После чистки `docker system prune --volumes` на проде пропала база. Почему и что делать?

Том остался без контейнера, и команда его удалила. Останавливаю новые записи, ищу последний бэкап или снапшот диска, восстанавливаю в новый том. Урок на будущее: бэкапы по расписанию и проверка восстановления, запрет `--volumes` в чистящих скриптах.

**Что хотят услышать:** что считается неиспользуемым томом, восстановление из бэкапа, профилактика.

**Красный флаг:** «данные из тома можно достать из `/var/lib/docker`, там всё осталось».

### 5. [junior] Два контейнера запущены, но один не может открыть `http://db:5432`: `Name or service not known`. Твои действия?

Проверю, в одной ли они сети: `docker inspect` по обоим, ключ `Networks`. Если сети разные или это default bridge, подключу к пользовательской: `docker network connect`. Затем `getent hosts db` внутри клиента и проверка порта.

**Что хотят услышать:** пользовательская сеть с DNS, default bridge без DNS, `network connect`.

**Красный флаг:** «пропишу IP контейнера в конфиг».

### 6. [middle] Приложение в контейнере слушает 127.0.0.1:8080, `-p 8080:8080` указан, но с хоста connection reset. Почему?

Внутри контейнера `127.0.0.1` это его собственный loopback, трафик от моста Docker приходит на другой интерфейс. Приложение должно слушать `0.0.0.0`. Проверю `docker exec ... ss -tln` (или `/proc/net/tcp`, если утилит нет) и логи запуска.

**Что хотят услышать:** loopback контейнера, `0.0.0.0`, публикация порта это DNAT на IP контейнера.

**Красный флаг:** «нужно `--network host`».

### 7. [junior] Что делает `-p 127.0.0.1:8080:8080` и чем отличается от `EXPOSE`?

`-p` публикует порт: Docker настраивает NAT так, что хост слушает 8080 только на loopback и пересылает трафик в контейнер. `EXPOSE` только метаданные образа, портов не открывает. Указывать `127.0.0.1` важно: без него порт открыт на всех интерфейсах, и Docker при этом обходит ufw.

**Что хотят услышать:** DNAT, привязка к интерфейсу, `EXPOSE` документация, ufw и Docker.

**Красный флаг:** «`EXPOSE` открывает порт наружу».

### 8. [middle] Как сделать бэкап тома, если контейнер работает и нет доступа в `/var/lib/docker`?

Запускаю одноразовый контейнер с монтированием тома (`:ro`) и каталога хоста, внутри `tar czf`. Для восстановления зеркально распаковываю в новый том. Для баз данных копия файлов работающего сервера может быть неконсистентной, там используют дамп (`pg_dump`) или снапшот.

**Что хотят услышать:** временный контейнер, `:ro`, консистентность, проверка восстановления.

**Красный флаг:** «копирую `/var/lib/docker/volumes` целиком, пока всё работает».

### 9. [middle] Контейнер работает под uid 10001, bind mount с хоста даёт `Permission denied`. Что делаешь?

Смотрю `ls -ln` на каталог: владелец числовой. Отдаю каталог нужному uid: `chown 10001:10001`, либо использую именованный том, унаследовавший права из образа. `chmod 777` и запуск от root не предлагаю: это лечит симптом и ломает безопасность.

**Что хотят услышать:** числовые uid, chown, том вместо bind, принцип минимальных прав.

**Красный флаг:** «запущу контейнер от root или сделаю 777».

### 10. [middle] Что произойдёт с IP-адресами, если пересоздать контейнеры, и как на это влияет выбор способа связи между сервисами?

Адреса могут поменяться, особенно если контейнеры стартуют в другом порядке. Поэтому сервисы обращаются друг к другу по имени через DNS Docker, а не по IP. Как следствие, имя контейнера должно быть стабильным и уникальным в сети. Тот же принцип в Compose и Kubernetes.

**Что хотят услышать:** DNS 127.0.0.11, имя вместо IP, стабильные имена, `--network-alias`.

**Красный флаг:** «зафиксирую IP статически в каждом конфиге».
