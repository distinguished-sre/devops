## Зачем это нужно

Половина инцидентов на новых серверах звучит одинаково: `Permission denied`. Сервис не может записать файл, не может прочитать конфиг, не может открыть сокет. Самое частое "лечение" со Stack Overflow: `chmod -R 777` или запуск от root. Оно работает и ломает безопасность: любой процесс на машине получает право читать и портить твои данные.

Правильный подход короткий: у сервиса свой пользователь, у пользователя ровно те права, которые нужны, а админские действия идут через `sudo` с узким списком разрешённого.

Шаг проекта: «Заметки» переезжают на сервер: системный пользователь `notes`, данные в `/var/lib/notes` (750), код в `/opt/notes/` (владелец root), а `app.py` получает файловое хранилище и `/healthz` (версия v2).

## Теория

### Пользователи, группы и где они хранятся

Для ядра пользователь это число: идентификатор пользователя (UID, user id). Имя `notes` нужно людям, ядро видит, например, `998`. Так же у групп есть GID. Нулевой UID у root, и именно он даёт суперправа, а не имя.

Учётные записи лежат в обычных текстовых файлах:

- `/etc/passwd` - имя, UID, GID, домашний каталог, оболочка (shell). Читают все, хэшей паролей там давно нет (стоит `x`), поэтому файл открыт.
- `/etc/shadow` - хэши паролей (password hashes). Читает только root.
- `/etc/group` - группы и их участники.

Человеческий пользователь имеет UID от 1000, системный (для сервисов) обычно меньше 1000. Системному пользователю не нужны домашний каталог и вход в систему: ему ставят оболочку `/usr/sbin/nologin`, и зайти под ним по SSH нельзя.

Пользователь состоит в основной группе и в дополнительных (supplementary groups). Права проверяются по всем сразу. Важная ловушка: после `usermod -aG docker alice` новая группа появится только в новой сессии входа.

### Права rwx: чтение, запись, запуск

В выводе `ls -l` первый символ это тип (`-` файл, `d` каталог, `l` ссылка), дальше три тройки: владелец (user), группа (group), остальные (other).

```text
-rwxr-x--- 1 notes notes 2048 Sep 29 10:00 app.py
```

Права записывают числом: `r`=4, `w`=2, `x`=1, складываем в каждой тройке. `750` значит владельцу `rwx`, группе `r-x`, остальным ничего. Запоминай четыре числа: `600` (секрет для одного), `640` (владелец пишет, группа читает), `644` (все читают), `755` (все читают и запускают, пишет владелец).

Проверяется только одна тройка: владелец смотрит по правам владельца, участник группы по группе, остальные по "остальным". Владелец с `000` не прочитает свой файл (root это не касается).

На каталогах те же биты значат другое:

- `r` - видеть список имён внутри;
- `w` - создавать, удалять и переименовывать файлы внутри (права на сам файл не важны);
- `x` - "проходить" через каталог: обращаться к файлам по имени, делать `cd`.

Поэтому каталог данных, куда сервис пишет, должен иметь `x` и `w` для сервиса.

> **Проверь понимание:** у файла `/srv/data/report.txt` права `644`, но `Permission denied` при чтении. Каталог `/srv/data` имеет `700` и владельца root. Ты обычный пользователь. Почему?

<details>
<summary>Ответ</summary>

Чтобы добраться до файла, нужен бит `x` на каждом каталоге пути. У `/srv/data` для остальных нет ничего, до файла ты не доходишь, права самого файла не проверяются. Быстрая проверка: `namei -l /srv/data/report.txt` показывает права по всему пути.

</details>

### chmod, chown, umask

`chown notes:notes файл` меняет владельца и группу (только root). `chmod` меняет права двумя способами: числом (`chmod 640 f`) или символами (`chmod u+x,g-w,o= f`, где `u` владелец, `g` группа, `o` остальные, `a` все). Число удобно, когда знаешь итог, символы когда меняешь один бит.

Права нового файла определяет маска создания (umask): из максимума (`666` для файлов, `777` для каталогов) вычитаются биты маски. Типичный `umask 022` даёт файлы `644` и каталоги `755`. `umask 077` даёт `600` и `700`: всё только для владельца. Маска действует на процесс, который создаёт файл. Поэтому файл, созданный сервисом, получает права по маске сервиса, а не твоей.

Особые биты: setuid (`4000`) запускает программу с правами её владельца (так работают `sudo` и `passwd`, такие файлы опасны); setgid (`2000`) на каталоге наследует группу; sticky bit (`1000`) запрещает удалять чужие файлы (так устроен `/tmp`, буква `t`).

### sudo и sudoers

`su` переключает тебя на другого пользователя с его паролем. `sudo` выполняет одну команду от имени другого (по умолчанию root) и просит твой пароль, а не пароль root. Кто и что может, описывает `/etc/sudoers` и файлы каталога `/etc/sudoers.d/`. Правило читается так:

```text
deploy ALL=(root) NOPASSWD: /usr/bin/du -sh /var/log
```

Пользователь `deploy`, на любых хостах, от имени root, без пароля, только эту команду с такими аргументами. Путь к команде абсолютный, иначе подмена через `PATH`.

Ошибка синтаксиса в sudoers ломает `sudo` целиком, и ты остаёшься без root. Поэтому три правила: править только через `visudo` (или проверять файл `visudo -cf файл`), кладёшь отдельным файлом в `sudoers.d` с правами `440`, и пока не проверил, держишь открытой вторую сессию с root-доступом.

Нужна Ubuntu (ВМ или WSL2) и пользователь с `sudo`. Сначала выполни `id` и `grep "^$(whoami):" /etc/passwd`: найди свой UID и группы.

### Задание 1. Права числами, каталоги и umask

**Цель:** научиться предсказывать права и понять, что делает `x` на каталоге.

<summary>Ответ</summary>

### Задание 2. sudo на одну команду без риска

**Цель:** выдать пользователю право на одну команду, проверить файл до применения и убедиться, что остальное запрещено.

**Предскажи:** что произойдёт, если положить в `/etc/sudoers.d/` файл с опечаткой и не проверять его `visudo -cf`?

<details>
<summary>Ответ</summary>

`sudo` прочитает битый файл и откажется работать: `sudo: /etc/sudoers.d/...: syntax error`. На сервере без root-входа ты теряешь админский доступ. Поэтому файл сначала проверяют в другом месте.

</details>

**Шаги**

1. Создай пользователя без пароля (входить под ним не будем, только `sudo -u`):

```bash

```

2. Открой вторую сессию терминала с `sudo -v` (она тебя подстрахует), а в первой сформируй правило в обычном файле и проверь:

```bash
printf 'deploy ALL=(root) NOPASSWD: /usr/bin/du -sh /var/log\n' > ~/deploy-du.tmp

```

3. Только после `parsed OK` установи файл с правильным владельцем и режимом и проверь работу:

```bash
sudo install -m 440 -o root -g root ~/deploy-du.tmp /etc/sudoers.d/deploy-du
rm ~/deploy-du.tmp
sudo visudo -c
sudo -u deploy sudo -n /usr/bin/du -sh /var/log
sudo -u deploy sudo -n cat /etc/shadow
```

**Что должно получиться**

```text

```

Размер у тебя свой. В новых Ubuntu вместо классического sudo стоит его реализация sudo-rs: тогда последняя строка может звучать как `sudo: interactive authentication is required`. Смысл тот же: разрешена только одна команда.

**Объясни себе**

- Почему файл лежит в `sudoers.d`, а не в `/etc/sudoers`?

**Типичные ошибки**

- `>>> /home/ubuntu/deploy-du.tmp: syntax error near line 1 <<<`: опечатка в правиле, например пропущен `=`. Исправь файл, не устанавливая его.

### Задание 3. Проект: сервис живёт под пользователем notes

**Цель:** установить «Заметки» как на сервере: свой пользователь, каталог данных `750`, код в `/opt/notes/` под root, запуск через `sudo -u notes`. Это шаг сквозного проекта, после него `app.py` версии v2.

**Предскажи:** запустим сервис от `notes`, а код принадлежит root с `644`. Сможет ли сервис читать код? Сможет ли он его изменить?

<details>
<summary>Ответ</summary>

Читать сможет (`644`), изменить нет: писать может только root. Даже при взломе сервиса код не подменить.

</details>

**Шаги**

1. Обнови `~/notes/app.py` до v2 (замени файл целиком). Версия из эталона: [`project/notes/versions/v2.py`](https://github.com/distinguished-sre/devops/tree/devops/project/notes/versions/v2.py).

```python
#!/usr/bin/env python3
"""Заметки v2: файловое хранилище и /healthz."""
import json
import os
import sys
import threading
from datetime import datetime, timezone
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer
from urllib.parse import urlparse

VERSION = os.environ.get("APP_VERSION", "dev")
HOST = os.environ.get("HOST", "127.0.0.1")
DATA = os.environ.get("NOTES_DATA", "/var/lib/notes/notes.txt")
try:
    PORT = int(os.environ.get("PORT", "8080"))
except ValueError:
    print("ошибка: PORT должен быть числом", file=sys.stderr)
    sys.exit(2)

LOCK = threading.Lock()  # записи в файл идут по одной


def read_notes():
    """Одна заметка на строку, формат JSON. Нет файла: заметок нет."""
    try:
        with open(DATA, encoding="utf-8") as f:
            return [json.loads(line) for line in f if line.strip()]
    except FileNotFoundError:
        return []


def add_note(text):
    with LOCK:
        note = {
            "id": len(read_notes()) + 1,
            "text": text,
            "created_at": datetime.now(timezone.utc).isoformat(timespec="seconds"),
        }
        with open(DATA, "a", encoding="utf-8") as f:
            f.write(json.dumps(note, ensure_ascii=False) + "\n")
        return note["id"]


class Handler(BaseHTTPRequestHandler):
    def send(self, code, body, ctype="application/json; charset=utf-8"):
        data = body.encode("utf-8")
        self.send_response(code)
        self.send_header("Content-Type", ctype)
        self.send_header("Content-Length", str(len(data)))
        self.end_headers()
        self.wfile.write(data)

    def json(self, code, obj):
        self.send(code, json.dumps(obj, ensure_ascii=False))

    def do_GET(self):
        path = urlparse(self.path).path
        if path == "/":
            self.send(200, f"Notes service v{VERSION}\n", "text/plain; charset=utf-8")
        elif path == "/healthz":
            self.send(200, "ok", "text/plain; charset=utf-8")
        elif path == "/readyz":
            ok = os.access(os.path.dirname(DATA), os.W_OK)
            self.send(200 if ok else 503, "ready" if ok else "not ready",
                      "text/plain; charset=utf-8")
        elif path == "/notes":
            try:
                self.json(200, read_notes())
            except OSError as e:
                print(f"ошибка хранилища: {e}", file=sys.stderr)
                self.json(500, {"error": "storage"})
        else:
            self.json(404, {"error": "not found"})

    def do_POST(self):
        if urlparse(self.path).path != "/notes":
            self.json(404, {"error": "not found"})
            return
        try:
            length = int(self.headers.get("Content-Length", "0"))
            text = json.loads(self.rfile.read(length))["text"]
        except (ValueError, KeyError, TypeError):
            self.json(400, {"error": "нужен JSON {\"text\": \"...\"}"})
            return
        if not isinstance(text, str) or not text.strip() or len(text) > 1000:
            self.json(400, {"error": "text: от 1 до 1000 символов"})
            return
        try:
            self.json(201, {"id": add_note(text)})
        except OSError as e:
            print(f"ошибка хранилища: {e}", file=sys.stderr)
            self.json(500, {"error": "storage"})

    def log_message(self, fmt, *args):
        if self.path not in ("/healthz", "/readyz"):
            print(f"{self.address_string()} {fmt % args}", file=sys.stderr)


if __name__ == "__main__":
    print(f"Notes v{VERSION} слушает {HOST}:{PORT}, данные {DATA}", file=sys.stderr)
    ThreadingHTTPServer((HOST, PORT), Handler).serve_forever()
```

### Исправление

<details>
<summary>Разбор всех сценариев</summary>

**Сценарий 1.** Каталог или файл принадлежат root (например, файл создали `sudo` при отладке), у `notes` нет права записи. Проверка: `stat` показывает `root:root` или отсутствует `w` для владельца. Исправление минимально нужным:

```bash
sudo chown -R notes:notes /var/lib/notes
sudo chmod 750 /var/lib/notes
sudo chmod 640 /var/lib/notes/notes.txt
```

**Сценарий 2.** Битый файл в `sudoers.d` ломает весь `sudo`. Если у тебя есть вторая сессия с root (или `su` с паролем root, или консоль ВМ), исправь: `visudo -c` покажет файл и строку с ошибкой, удали или поправь его (`sudo rm /etc/sudoers.d/имя`). Без второй сессии придётся входить через консоль провайдера или режим восстановления. Урок: правило не попадает в `sudoers.d`, пока `visudo -cf` не сказал `parsed OK`, и режим у файла `440`.

**Сценарий 3.** `777` выдан рекурсивно: ошибку прав он скрыл, но открыл данные всем. Верни правильные права:

```bash
sudo chown -R notes:notes /var/lib/notes
sudo chmod 750 /var/lib/notes
sudo find /var/lib/notes -type f -exec chmod 640 {} +
```

</details>

## Вопросы с собеседований

### 1. [junior] Что значит 755, 644 и 600 и где ты их применяешь?

`755`: владелец читает, пишет, запускает, остальные читают и запускают. Это каталоги и исполняемые файлы. `644`: владелец пишет, все читают: обычные файлы. `600`: только владелец: ключи, токены, пароли.

**Что хотят услышать:** разбор по цифрам (4, 2, 1), три примера использования, для каталога `x` значит "проходить".

**Красный флаг:** "755 это когда файл виден всем" без объяснения битов.

### 2. [junior] Сервис пишет лог, а получает `Permission denied`. Как разберёшься?

Сначала узнаю, от кого работает процесс (`ps -o user`), затем смотрю права на файл и на каждый каталог пути (`namei -l`). Проверяю запись от имени пользователя сервиса (`sudo -u svc touch ...`). Правлю владельца или группу, а не открываю всем.

**Что хотят услышать:** `namei -l`, проверка `x` на каталогах пути, `sudo -u`, "минимально нужные права".

**Красный флаг:** сразу `chmod 777` или запуск от root.

### 3. [junior] Зачем запускать сервис не от root?

Если сервис взломают, у злоумышленника будут права процесса. От root это вся система, от отдельного пользователя только его данные. Ещё меньше ущерба от ошибок: баг удаления не заденет систему.

**Что хотят услышать:** принцип наименьших привилегий (least privilege), отдельный пользователь на сервис, код только для чтения.

**Красный флаг:** "root удобнее, не нужно возиться с правами".

### 4. [junior] В чём разница между `su` и `sudo`?

`su` переключает на другого пользователя, нужен его пароль. `sudo` выполняет одну команду от имени другого по правилам sudoers, требует твой пароль и пишет в журнал.

**Что хотят услышать:** аудит команд, отсутствие общего пароля root, тонкая настройка правил.

**Красный флаг:** "sudo это просто su с другим названием".

### 5. [junior] Файл `644`, но ты получаешь отказ при чтении. Что проверишь?

Права на каталоги пути (нужен `x`), не мешает ли группа или владелец, не стоит ли ACL или ограничение mount. Смотрю `namei -l путь`.

**Что хотят услышать:** проверка всех каталогов пути, `namei`, `id` для групп текущего пользователя.

**Красный флаг:** смотрит только на права файла.

### 6. [junior] Что такое umask и почему файл, созданный сервисом, отличается по правам от твоего?

Это маска, вычитаемая из `666` для файлов и `777` для каталогов при создании. Маска относится к процессу, и у сервиса она своя. У меня `022` даёт `644`, у сервиса может быть `077` и `600`.

**Что хотят услышать:** вычитание битов, привязка к процессу, где задаётся (для сервисов в unit-файле `UMask=`, тема 1.8).

**Красный флаг:** "umask это права по умолчанию для всех файлов на системе".

### 7. [middle] Тебе нужно, чтобы разработчик мог перезапускать один сервис и больше ничего. Как выдашь?

Отдельный файл в `/etc/sudoers.d/` c правилом на конкретную команду с абсолютным путём и аргументами, режим `440`. Проверяю `visudo -cf` до установки и держу вторую сессию. Запрещаю `sudo` без аргументов и wildcards в опасных местах.

**Что хотят услышать:** `visudo -cf`, `sudoers.d`, абсолютный путь, риск шаблонов (`*` позволяет добавить аргументы и обойти ограничение), `sudo -l -U`.

**Красный флаг:** "добавлю в группу sudo" или `ALL=(ALL) NOPASSWD: ALL`.

### 8. [middle] Прод после чьей-то правки отвечает 500, в логе `Permission denied` на `/var/lib/app/data`. Коллега предлагает `chmod -R 777`. Твои действия?

Отказываюсь. Смотрю `stat` и `namei -l`, выясняю, кто владелец процесса и что изменилось (деплой мог создать файлы от root). Возвращаю владельца `chown -R app:app` и режим `750` на каталог, `640` на файлы. Проверяю запись от имени `app` и перезапускаю. Причину закрепляю: деплой не должен запускаться от root.

**Что хотят услышать:** диагностика раньше действий, минимальные права, поиск первопричины (кто создал файлы), исключение root из процесса деплоя.

**Красный флаг:** согласие на `777` "временно".

### 9. [middle] Ты добавил пользователя в группу `docker` (или другую), но доступа всё ещё нет. Почему?

Группы читаются при входе. Текущая сессия и уже запущенные процессы получают старый список. Нужен новый вход (`newgrp` или перелогин), проверяю `id`. Отдельно помню: `docker` это де-факто root, группу выдают осознанно.

**Что хотят услышать:** `id` против `getent group`, новая сессия, безопасность группы docker.

**Красный флаг:** перезагружает сервер.

### 10. [middle] Что такое setuid, зачем он нужен и чем опасен?

Бит на исполняемом файле: процесс работает с правами владельца файла. Так `passwd` меняет `/etc/shadow`, обычному пользователю запись туда недоступна. Опасно: уязвимость в такой программе даёт root. Аудит: `find / -perm -4000 -type f`, лишние снимаю или убираю.

**Что хотят услышать:** пример (`passwd`, `sudo`), `find -perm -4000`, поиск на скрипты (в скриптах игнорируется), `nosuid` при монтировании.

**Красный флаг:** "это просто права на запуск".

## Проверено на версиях

- Ubuntu Server: 26.04 LTS и 24.04 LTS
- coreutils, util-linux, shadow (`useradd`, `chmod`, `stat`, `namei`): из репозитория Ubuntu
- sudo: версия не закреплена, проверь актуальную версию на странице проекта (в новых Ubuntu может стоять sudo-rs, сообщения об ошибках чуть отличаются)
- Python: 3.13 (код `app.py` использует только стандартную библиотеку)
