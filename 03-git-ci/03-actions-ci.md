## Зачем это нужно

В [уроке 3.2](02-remotes-workflow.md) ты научился вливать код через Pull Request, но проверял его глазами и руками. Человек устаёт, забывает запустить тесты и вливает то, что «у меня работает». На работе это заканчивается сломанным main в пятницу вечером: кто-то ломает синтаксис, тесты не запущены, релиз падает.

Непрерывная интеграция (Continuous Integration, CI) делает проверку обязательной и одинаковой для всех: на каждый Pull Request чистая машина скачивает код, ставит зависимости, гоняет линтер и тесты, а результат виден прямо в PR. Красный статус не даёт слить код в main. Этот навык спрашивают на любом собеседовании на DevOps.

Шаг проекта: в «Заметках» появляются `.github/workflows/ci.yml` (jobs `lint` и `test` с matrix Python 3.13 и 3.14), `requirements-dev.txt` и `ruff.toml`, а main требует зелёного CI.

## Теория

### Из чего состоит workflow

Автоматизация в GitHub Actions описывается файлом YAML в каталоге `.github/workflows/`. Один файл это один рабочий процесс (workflow). Вот словарь, который нужен весь урок:

- **Событие (event)** запускает workflow: `push`, `pull_request`, расписание `schedule`, ручной запуск `workflow_dispatch`.
- **Задача (job)** это набор шагов, который выполняется на одной машине. Разные jobs по умолчанию идут параллельно.
- **Шаг (step)** это либо команда оболочки (`run:`), либо готовое действие (`uses:`).
- **Действие (action)** это переиспользуемый кусок автоматизации из каталога GitHub, например `actions/checkout` скачивает код репозитория.
- **Раннер (runner)** это машина, на которой идёт job. `ubuntu-24.04` это виртуальная машина, которую GitHub создаёт на время job и удаляет после. Всё, что ты поставил, исчезнет: каждый запуск начинается с чистого листа.

Отсюда главное следствие: CI не видит ничего, чего нет в репозитории. Ни твоего venv, ни файла `.env`, ни игнорируемых файлов. Если код работает только у тебя, CI покажет это первым.

Шаг проходит, если команда вернула код выхода 0 (ты видел коды выхода в [уроке 1.6](../01-linux/06-bash-basics.md)). Любой другой код делает шаг красным, остальные шаги job пропускаются, job красный.

> **Проверь понимание:** ты поставил на раннере `pip install ruff` в первом job. Будет ли ruff доступен во втором job того же workflow?

<details>
<summary>Ответ</summary>

Нет. Каждый job идёт на своей чистой машине. Если ruff нужен во втором job, его ставят там снова (или передают результат через артефакт, но для установки инструментов это не нужно).

</details>

### События: push и pull_request

Для проверки кода хватает двух событий:

- `pull_request` запускается при открытии PR и при каждом новом коммите в ветку PR. GitHub проверяет не саму ветку, а **результат слияния ветки с main** (merge commit), то есть ровно то, что окажется в main.
- `push` в `main` запускается после слияния. Это страховка: main всегда проверен.

Если написать просто `on: push`, workflow запустится на каждый push в любую ветку. Вместе с PR получится двойная работа: один коммит проверяется дважды. Поэтому `push` ограничивают веткой main.

Событие `pull_request_target` похоже по названию, но опасно: оно запускается в контексте основного репозитория, с доступом к секретам, даже для PR из чужого форка. Для обычной проверки кода оно не нужно. Подробно про риски в [уроке 3.4](04-quality-security-ci.md).

> **Проверь понимание:** почему для PR полезнее проверять merge commit, а не саму ветку?

<details>
<summary>Ответ</summary>

Ветка могла отстать от main. Тесты на ветке зелёные, но после слияния с новым main они могут упасть (чужое изменение конфликтует по смыслу). Проверка merge commit ловит это до слияния.

</details>

### Matrix, кэш, concurrency, permissions

**Matrix** запускает один job несколько раз с разными параметрами. Для нас это версии Python: код должен работать и на 3.13, и на 3.14. GitHub создаст два параллельных job. По умолчанию, если один упал, остальные отменяются; `fail-fast: false` отключает отмену, чтобы ты видел все красные сразу.

**Кэш (cache)** ускоряет повторные запуски: скачанные пакеты pip сохраняются между запусками по ключу (хэш файла зависимостей). Действие `setup-python` умеет это само через `cache: pip`. Кэш это оптимизация: его можно потерять, и workflow обязан работать без него. Он отличается от **артефакта (artifact)**: артефакт это результат запуска (отчёт, собранный архив), который ты хочешь скачать или передать другому job.

**Concurrency** с `cancel-in-progress: true` отменяет устаревший запуск, если в ту же ветку прилетел новый коммит. Это экономит минуты и убирает гонку результатов.

**Permissions** ограничивают права автоматически выдаваемого токена `GITHUB_TOKEN`. Для проверки кода нужно только чтение: `contents: read`. Принцип наименьших привилегий (least privilege) работает и здесь: если в проверку проникнет чужой код, токен не позволит ему писать в репозиторий.

> **Проверь понимание:** чем кэш pip отличается от артефакта и что произойдёт, если кэш пропал?

<details>
<summary>Ответ</summary>

Кэш это ускорение установки зависимостей, он не является результатом работы. Если он пропал, workflow просто скачает пакеты заново, станет медленнее, но результат тот же. Артефакт это результат job, который нужно сохранить и скачать.

</details>

### Закрепление версий действий

`uses: actions/checkout@v7.0.1` ссылается на тег. Тег в чужом репозитории можно передвинуть, и в твой CI приедет другой код. Для чувствительных workflow (публикация, деплой) действие закрепляют по SHA коммита: `uses: actions/checkout@<40 символов>  # v7.0.1`. Мы в этом уроке закрепляем по точным тегам, без `@main` и без плавающих `@v7`, а про SHA и обновления через Dependabot поговорим в [уроке 3.4](04-quality-security-ci.md).

## Практика

Все задания выполняются в репозитории `~/notes`, который ты завёл в [уроке 3.2](02-remotes-workflow.md). Работаем через ветки и Pull Request, как договорились.

### Задание 1. Линтер локально и конфиги

**Цель:** запустить ruff у себя, чтобы CI не стал первым, кто увидит замечания.

**Предскажи:** в `~/notes` лежит `app.py` версии v3. Найдёт ли ruff с минимальным набором правил (`E`, `F`) замечания в нём? Как ты объяснишь результат?

<details>
<summary>Ответ</summary>

Скорее всего нет: правила E (стиль pycodestyle) и F (pyflakes: неиспользуемые импорты, неопределённые имена) ловят мелочи, а код курса написан чисто. Если замечание всё же нашлось, это настоящий мусор в коде, а не ошибка ruff.

</details>

**Шаги:**

1. Создай ветку и виртуальное окружение (venv) для инструментов разработки:

```bash
cd ~/notes
git switch main && git pull
git switch -c ci/add-workflow
python3 -m venv .venv
source .venv/bin/activate
```

2. Создай `requirements-dev.txt`. Версия ruff в курсе не закреплена, ставится актуальная:

```bash
cat > requirements-dev.txt <<'EOT'
# Инструменты разработки. Версии не закреплены: ставится актуальная.
ruff
EOT
pip install -r requirements-dev.txt
```

3. Создай `ruff.toml`:

```bash
cat > ruff.toml <<'EOT'
# Настройки ruff для проекта «Заметки»
line-length = 120
target-version = "py313"

[lint]
# E: стиль pycodestyle, F: pyflakes (неиспользуемые импорты и переменные)
select = ["E", "F"]
EOT
```

4. Запусти линтер и проверку синтаксиса:

```bash
ruff check .
python -m py_compile app.py test_app.py && echo "синтаксис ок"
```

**Что должно получиться:**

```text
All checks passed!
синтаксис ок
```

**Объясни себе:**
- Почему `.venv/` есть в `.gitignore` из урока 3.1 и что будет, если его закоммитить?
- Чем `py_compile` отличается от запуска приложения?

**Типичные ошибки:**
- `error: externally-managed-environment`: `pip` пытается писать в системный Python. Активируй venv: `source .venv/bin/activate`.
- `bash: ruff: command not found`: venv не активирован или пакет не установлен. Проверь приглашение (`(.venv)`) и повтори `pip install -r requirements-dev.txt`.
- `F401 [*] 'os' imported but unused`: это не ошибка настройки, а реальное замечание. Удали лишний импорт или запусти `ruff check --fix .`.

### Задание 2. Первый workflow

**Цель:** написать `ci.yml`, запустить его в PR и прочитать результат.

**Предскажи:** сколько job увидишь во вкладке Actions после первого push и сколько из них пойдёт параллельно? Ответ: по файлу ниже, до запуска.

<details>
<summary>Ответ</summary>

Три запуска job: `lint` и два `test` (для 3.13 и 3.14). Все три параллельны, потому что между ними нет `needs`.

</details>

**Шаги:**

1. Создай каталог и файл. Комментарии в файле читай внимательно, это разбор:

{% raw %}
```bash
mkdir -p .github/workflows
cat > .github/workflows/ci.yml <<'EOT'
name: CI

# Когда запускать: на каждый PR и на push в main (после слияния)
on:
  pull_request:
  push:
    branches: [main]

# Токену достаточно читать код
permissions:
  contents: read

# Новый коммит в ту же ветку отменяет устаревший запуск
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

jobs:
  lint:
    runs-on: ubuntu-24.04
    steps:
      # Скачать код репозитория на раннер
      - uses: actions/checkout@v7.0.1

      - uses: actions/setup-python@v7.0.0
        with:
          python-version: "3.13"
          cache: pip
          cache-dependency-path: requirements-dev.txt

      - name: Установить инструменты
        run: pip install -r requirements-dev.txt

      # Самое дешёвое идёт первым: если синтаксис сломан, узнаем за секунды
      - name: Проверить синтаксис
        run: python -m py_compile app.py test_app.py

      - name: Линтер ruff
        run: ruff check .

  test:
    runs-on: ubuntu-24.04
    strategy:
      # Пусть упавшая версия не скрывает результат другой
      fail-fast: false
      matrix:
        python-version: ["3.13", "3.14"]
    steps:
      - uses: actions/checkout@v7.0.1

      - uses: actions/setup-python@v7.0.0
        with:
          python-version: ${{ matrix.python-version }}

      # Внешних зависимостей у сервиса нет, ставить нечего
      - name: Тесты
        run: python -m unittest -v
EOT
```
{% endraw %}

2. Проверь YAML локально и отправь ветку:

```bash
python3 -c "import yaml" 2>/dev/null || pip install pyyaml
python3 -c "import yaml,sys; yaml.safe_load(open('.github/workflows/ci.yml')); print('yaml ок')"
git add .github/workflows/ci.yml requirements-dev.txt ruff.toml
git commit -m "Добавить CI: линтер и тесты на Python 3.13 и 3.14"
git push -u origin ci/add-workflow
```

3. Открой Pull Request (`gh pr create --fill` или через сайт). Внизу страницы PR найди блок проверок, открой запуск и разверни шаги job `lint`.

**Что должно получиться:** в PR три проверки, все зелёные:

```text
CI / lint (pull_request)            Successful
CI / test (3.13) (pull_request)     Successful
CI / test (3.14) (pull_request)     Successful
```

**Объясни себе:**
- Почему `checkout` нужен в каждом job?
- Что произойдёт, если в `test_app.py` тест упадёт только на 3.14, и при чём тут `fail-fast: false`?
- Почему `ruff check` идёт после `py_compile`, а не наоборот?

**Типичные ошибки:**
- Workflow не появился во вкладке Actions: файл лежит не в `.github/workflows/` или расширение не `.yml`/`.yaml`.
- `Invalid workflow file: .github/workflows/ci.yml#L12` и `You have an error in your yaml syntax`: сбитые отступы или табуляция вместо пробелов. YAML понимает только пробелы.
- `Error: Unable to resolve action actions/checkout@v7, unable to find version v7`: тега `v7` в этом виде нет. Пиши полный тег из урока, `v7.0.1`.
- `ModuleNotFoundError: No module named 'app'`: тесты запускаются не из корня репозитория. `python -m unittest` ищет модули в текущем каталоге, поэтому шаг идёт без `working-directory`.

### Задание 3. Красный PR не пускает в main

**Цель:** сломать тест намеренно, увидеть красный статус и закрыть слияние.

**Предскажи:** что покажет кнопка слияния в PR, если хотя бы одна проверка красная и main ещё не требует проверок? А если потребует?

<details>
<summary>Ответ</summary>

Без правила GitHub покажет предупреждение, но кнопка останется рабочей: слить можно. Когда в защите main включено «Require status checks to pass», кнопка блокируется, пока все выбранные проверки не зелёные.

</details>

**Шаги:**

1. Сначала слей первый PR (зелёный) и включи обязательные проверки. В репозитории: Settings, Rules (или Branches), правило для `main` из урока 3.2, включи **Require status checks to pass before merging** и добавь проверки `lint`, `test (3.13)`, `test (3.14)`. Проверки появляются в списке после того, как хотя бы раз отработали.

2. Создай ветку с намеренной поломкой. Правь одно ожидание в тесте (пример: тест на `/healthz` ждёт 200, поменяй на 500):

```bash
git switch main && git pull
git switch -c ci/break-test
grep -n "200" test_app.py | head
```

Поменяй в найденном тесте `/healthz` число `200` на `500` и сохрани.

```bash
python -m unittest 2>&1 | tail -5
git commit -am "Проверка: красный тест"
git push -u origin ci/break-test
gh pr create --fill
```

3. Открой PR, посмотри статус и попытайся слить.

4. Почини тест обратным изменением, сделай новый коммит в ту же ветку, дождись зелёного и слей.

**Что должно получиться:** в PR красные `test (3.13)` и `test (3.14)`, кнопка слияния заблокирована:

```text
CI / lint (pull_request)            Successful
CI / test (3.13) (pull_request)     Failing
CI / test (3.14) (pull_request)     Failing
Merging is blocked
Required statuses must pass before merging.
```

**Объясни себе:**
- Почему `lint` остался зелёным, а `test` красный, хотя это один workflow?
- Почему после нового коммита в ветку проверка перезапустилась сама?
- Кто может обойти блокировку и должен ли администратор это делать?

**Типичные ошибки:**
- `AssertionError: 200 != 500` в логе: это и есть ожидаемая поломка, смотри строку под `FAIL:`.
- Проверок нет в списке обязательных: имя в правиле должно совпадать с именем job (для matrix это `test (3.13)`), и проверка должна хотя бы раз отработать.
- Кнопка слияния всё равно активна у владельца репозитория: у владельца правило можно обходить (bypass). Включи «Do not allow bypassing the above settings».

## Сломай и почини

Скачай скрипт поломок и запусти сценарий. Сам скрипт не читай: цель в том, чтобы найти причину по симптомам, как на работе.

```bash
cd ~/notes
git switch main && git pull && git switch -c ci/break-drill
curl -fsSL -o /tmp/break33.sh https://raw.githubusercontent.com/distinguished-sre/devops/devops/project/notes/break/3.3/break.sh
bash /tmp/break33.sh 1        # сценарии 1, 2, 3 или random
git commit -am "break drill" && git push -u origin ci/break-drill
gh pr create --fill
rm /tmp/break33.sh
```

После разбора каждого сценария закрывай PR без слияния и возвращайся на main.

### Симптом

Три разных красных PR:

1. Во вкладке Actions запуска нет вообще, а на странице файла workflow красная плашка.
2. Job красный, в логе последний шаг заканчивается строкой `Error: Process completed with exit code 1.`
3. Тесты зелёные у тебя в терминале, но красные в CI.

### Гипотезы

- Сценарий 1: workflow не разобран как YAML (отступы, двоеточие, кавычки) или не найден.
- Сценарий 2: команда в шаге вернула ненулевой код. Это не поломка Actions, а результат твоей команды.
- Сценарий 3: раннер отличается от твоей машины: версия Python, отсутствующие файлы, порядок тестов, время, локаль, данные, которые лежат у тебя, но не в git.

### Проверки

```bash
# Сценарий 1: разобрать YAML локально, ошибка покажет строку
python3 -c "import yaml; yaml.safe_load(open('.github/workflows/ci.yml'))"

# Сценарий 2: найти первый упавший шаг и воспроизвести его команду у себя
gh run view --log-failed | head -40

# Сценарий 3: чем локальная среда отличается от раннера
python --version
git status --ignored --short
python -m unittest -v 2>&1 | tail -20
```

### Исправление

<details>
<summary>Разбор трёх сценариев</summary>

**Сценарий 1, синтаксис YAML.** Симптом: запуска нет, в интерфейсе `Invalid workflow file`. Локальная проверка вернёт что-то вроде `mapping values are not allowed here` со строкой и колонкой. Причина: сбитый отступ или табуляция. Исправление: выровнять по пробелам (два на уровень), проверить `yaml.safe_load`, закоммитить. Урок: файл workflow проверяй локально до push.

**Сценарий 2, exit code 1.** Симптом: `Error: Process completed with exit code 1.` Это последняя строка, но не причина. Причина выше по логу: строка `FAIL: test_...` или замечание ruff `E501`. Скопируй команду шага и запусти у себя ровно так же. Исправление: починить код или тест, а не «перезапустить job». Перезапуск красного детерминированного теста ничего не даёт.

**Сценарий 3, зелёный локально, красный в CI.** Типичные причины по убыванию частоты: (а) тест использует файл, который есть только у тебя и лежит в `.gitignore` (например, `data/`), поэтому `git status --ignored` его покажет; (б) разница версий Python: у тебя, например, 3.12, а CI прогоняет 3.13 и 3.14; (в) тест зависит от порядка выполнения или от занятого порта. Исправление: тест должен создавать всё нужное сам (временный каталог, порт 0, как в эталонном `test_app.py`), а локально ты воспроизводишь среду CI чистым клоном: `git clone . /tmp/cleanclone && cd /tmp/cleanclone && python -m unittest`.

Общий принцип: CI ничего не «ломает». Он показывает, какие зависимости от твоей машины были скрыты.

</details>

## Вопросы с собеседований

### 1. [junior] Чем отличаются CI, Continuous Delivery и Continuous Deployment?

CI это автоматическая сборка и проверка кода при каждом изменении. Continuous Delivery это ещё и готовность к выкладке в любой момент, но выкладка по кнопке. Continuous Deployment выкатывает в прод сам, если проверки зелёные.

**Что хотят услышать:** границу между «готово к выкладке» и «выкладывается само»; что CI это только про проверку.

**Красный флаг:** «CD это когда деплоят на сервер» без различия delivery и deployment.

### 2. [junior] Что такое runner и чем hosted отличается от self-hosted?

Runner это машина, на которой выполняется job. Hosted создаёт и уничтожает GitHub, среда чистая и одинаковая. Self-hosted это твой сервер: можно свои ресурсы, доступ во внутреннюю сеть, но чистоту и безопасность обеспечиваешь сам.

**Что хотят услышать:** чистая эфемерная среда против постоянной; риск запуска чужого кода на своей машине (особенно PR из форков).

**Красный флаг:** «self-hosted всегда лучше, он быстрее» без слов про безопасность и обслуживание.

### 3. [middle] Прод отвечает 502 после вчерашнего релиза, а CI был зелёный. Твои действия?

Сначала откатываю релиз на предыдущий известный рабочий, потом ищу причину. Зелёный CI лишь говорит, что проверки прошли, а не что прод здоров. Смотрю логи приложения и nginx, `/healthz`, что изменилось в релизе, различие окружений.

**Что хотят услышать:** порядок «сначала восстановить, потом разбирать»; понимание, что CI не покрывает конфиг и окружение прода; вывод: добавить проверку, которая поймала бы это (smoke-тест).

**Красный флаг:** «CI зелёный, значит дело не в нас» или «сначала найду виновного».

### 4. [middle] Тесты зелёные локально, красные в CI. С чего начнёшь?

Прочитаю лог первого упавшего шага, а не последнюю строку. Затем сравню среду: версия Python, файлы вне git (`git status --ignored`), переменные окружения, порядок тестов. Воспроизведу чистым клоном репозитория.

**Что хотят услышать:** чистый клон как метод; игнорируемые файлы; версии; что не надо просто перезапускать.

**Красный флаг:** «нажму Re-run, пока не станет зелёным».

### 5. [middle] Тест падает раз в десять запусков. Что делаешь?

Это нестабильный (flaky) тест. Не заглушаю перезапусками. Ищу причину: гонка, время, порядок, общий ресурс, зависимость от сети. Пока чиню, могу пометить тест и завести задачу, но с владельцем и сроком.

**Что хотят услышать:** что автоперезапуск маскирует баг; воспроизведение циклом (`for i in $(seq 50)`); изоляция данных теста.

**Красный флаг:** «отключу тест навсегда» или «поставлю retry 5».

### 6. [middle] Как не пустить красный код в main?

Защита ветки: обязательный Pull Request, обязательные проверки статуса, актуальность ветки, запрет прямого push и обхода правил для администраторов. Проверки указываются по имени job.

**Что хотят услышать:** «required status checks» и тонкость: без запуска хотя бы раз проверка не появится в списке; закрытый bypass.

**Красный флаг:** «договоримся в команде не сливать красное».

### 7. [middle] Пайплайн идёт 15 минут. Как ускорить?

Сначала измеряю, где время. Дальше: кэш зависимостей, параллельные jobs, самые быстрые проверки первыми (fail fast), отмена устаревших запусков через `concurrency`, запуск только нужного (фильтры путей), меньше matrix там, где она не нужна.

**Что хотят услышать:** «сначала измерить»; различие кэша и артефакта; параллелизм.

**Красный флаг:** «купить раннер помощнее» без анализа.

### 8. [junior] Зачем `permissions: contents: read` в workflow?

Токен `GITHUB_TOKEN` выдаётся каждому запуску. По умолчанию его права могут быть шире нужных. Ограничиваю до чтения: если в проверку попадёт вредоносный код или скомпрометированное действие, писать в репозиторий он не сможет.

**Что хотят услышать:** наименьшие привилегии; токен живёт только на время запуска.

**Красный флаг:** «а разве токен не всегда безопасен».

### 9. [middle] Чем `pull_request` отличается от `pull_request_target` и почему второй опасен?

`pull_request` из форка запускается с урезанными правами и без секретов. `pull_request_target` запускается в контексте основного репозитория с секретами. Если он выполняет код из PR, чужой код получает секреты.

**Что хотят услышать:** «не запускать код из PR в `pull_request_target`»; безопасные сценарии (только метки, комментарии).

**Красный флаг:** «оба одно и то же, просто названия».

### 10. [middle] В workflow подключено `uses: some-org/action@v2`. Что тебя беспокоит?

Тег можно передвинуть, и в мой CI приедет другой код. Для важных workflow закрепляю по SHA коммита с комментарием версии, а обновления поднимаю через Dependabot. Смотрю, кто автор, какие права требует и что действие делает.

**Что хотят услышать:** supply chain, SHA против тега, Dependabot; проверка источника.

**Красный флаг:** «это же популярное действие, значит безопасное».
