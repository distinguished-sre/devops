## Зачем это нужно

Ты правишь `app.py`, ломаешь его и не помнишь, как было раньше. Или коллега и ты правите один файл, и чья версия «настоящая», неясно. Git хранит снимки проекта, поэтому почти любую ошибку можно откатить, а историю можно читать как журнал изменений. На работе без него не живёт ни код, ни конфиги, ни Terraform, ни манифесты Kubernetes.

Половина инцидентов вида «кто это менял и когда» разбирается командой `git log`, а «потерял работу» чаще всего лечится через `git reflog`.

Шаг проекта: каталог `~/notes` становится git-репозиторием с `.gitignore` и `README.md`, первый коммит фиксирует «Заметки» v3.

## Теория

### Три области и коммит как снимок

В git у файла три места жизни:

```text
рабочий каталог  --git add-->  индекс (staging)  --git commit-->  история (.git)
   ты правишь                  черновик коммита                    зафиксированные снимки
```

- Рабочий каталог (working tree): файлы, которые ты видишь и правишь.
- Индекс (index, staging area): список того, что попадёт в следующий коммит.
- История: коммиты (commit) в каталоге `.git`.

Коммит это не «разница с прошлым разом», а снимок всего проекта плюс метаданные: автор, время, сообщение и ссылка на родителя (parent). Каждый коммит имеет имя-хеш (SHA-1, 40 символов; обычно показывают первые 7). Хеш считается от содержимого, включая родителя, поэтому незаметно изменить старый коммит нельзя: поменяется хеш и всех потомков.

Двухшаговость `add` и `commit` нужна, чтобы из десяти правок собрать два осмысленных коммита. `git status` показывает, что в какой области, и опытный инженер вызывает его десятки раз в день.

> **Проверь понимание:** ты изменил два файла, а `git add` сделал только для одного. Что попадёт в `git commit`?

<details markdown="1">
<summary>Ответ</summary>

Только проиндексированный файл, в том виде, каким он был в момент `add`. Второй останется изменённым в рабочем каталоге. Если ты правил первый файл после `add`, эти правки тоже не попадут в коммит, пока не сделаешь `add` ещё раз.

</details>

### HEAD, ветка и detached HEAD

Ветка (branch) это просто файл с хешем последнего коммита. Создание ветки стоит копейки: записывается 41 байт. `HEAD` указывает, где ты сейчас: обычно на ветку, а ветка на коммит. Новый коммит сдвигает ветку, на которой стоит `HEAD`.

Если `HEAD` указывает прямо на коммит (например, после `git switch --detach <хеш>` или `git checkout <хеш>`), это detached HEAD (отсоединённый HEAD). Коммиты там делать можно, но без ветки они потеряются при переключении: достаточно создать ветку `git switch -c спасение`.

> **Проверь понимание:** что делает команда `git branch feature`, когда ты стоишь на `main`?

<details markdown="1">
<summary>Ответ</summary>

Создаёт новый указатель `feature` на тот же коммит, что и `main`. Файлы не копируются, и ты остаёшься на `main`: `HEAD` не сдвигается. Перейти можно командой `git switch feature`, а создать и перейти одной командой `git switch -c feature`.

</details>

### Слияние: fast-forward и merge commit

`git merge ветка` вливает ветку в текущую. Если текущая ветка не уходила вперёд, git просто передвигает указатель (fast-forward, «перемотка»), новых коммитов нет. Если обе ветки получили свои коммиты, git создаёт merge commit с двумя родителями. Если обе правили одни и те же строки, будет конфликт; разбор конфликтов и `rebase` в [следующем уроке](02-remotes-workflow.md).

### Отмена: restore, reset и revert

Три команды, которые путают на собеседованиях:

| Команда | Что делает | Меняет историю? |
|---|---|---|
| `git restore файл` | возвращает файл из индекса (или `--source=HEAD`) в рабочий каталог | нет |
| `git revert хеш` | создаёт новый коммит, отменяющий указанный | нет, история только растёт |
| `git reset --soft/--mixed/--hard хеш` | двигает ветку на другой коммит | да, коммиты «выпадают» |

Режимы `reset`: `--soft` двигает только ветку (индекс и файлы остаются), `--mixed` (по умолчанию) ещё и сбрасывает индекс, `--hard` заодно перезаписывает рабочий каталог, то есть уничтожает незакоммиченные правки. Правило: то, что уже увидели другие, отменяют через `revert`; `reset` подходит только для локальных, ещё не отправленных коммитов.

> **Проверь понимание:** какая из трёх команд безопасна для коммита, который уже получили коллеги, и почему?

<details markdown="1">
<summary>Ответ</summary>

`revert`. Он не переписывает историю, а добавляет новый коммит с обратными изменениями, так что у коллег история продолжается без расхождений. После `reset` у них остались бы коммиты, которых у тебя нет.

</details>

### reflog: страховка от собственных ошибок

`git reflog` хранит журнал перемещений `HEAD` (по умолчанию около 90 дней для достижимых записей и 30 для недостижимых). Даже после `reset --hard` потерянный коммит ещё лежит в базе, и его можно найти по reflog и вернуть. Пока сборщик мусора (`git gc`) не убрал недостижимые объекты, работа не потеряна. Reflog локальный: на другой машине его нет.

### stash, bisect и удаление файлов

`git stash` откладывает незакоммиченные правки, `git stash pop` возвращает. `git bisect` ищет сломавший коммит двоичным поиском: 1000 коммитов примерно за 10 шагов. Удалять отслеживаемые файлы нужно `git rm файл`; `git rm --cached файл` убирает файл из git, но оставляет на диске.

### .gitignore и Conventional Commits

`.gitignore` перечисляет шаблоны файлов, которые git не отслеживает: секреты, логи, кэш, данные. Важная ловушка: он не действует на файлы, которые уже в индексе; их нужно убрать через `git rm --cached`.

Сообщения коммитов пишут по соглашению Conventional Commits: `тип: что сделано` в повелительном наклонении, например `feat: добавить /headers`, `fix: вернуть 405 на DELETE`, `docs: описать запуск`, `chore: добавить .gitignore`. Заголовок до 72 символов, отвечает на вопрос «что изменилось», а тело (если нужно) объясняет «почему».

### Задание 1. Репозиторий и путь файла через три области

**Цель:** увидеть, как файл проходит рабочий каталог, индекс и историю, и заглянуть в объекты.

**Предскажи:** после `git init` и создания файла что покажет `git status`: файл в «untracked» или в «changes to be committed»? А после `git add`?

<details markdown="1">
<summary>Ответ</summary>

Сначала untracked (git о нём не знает), после `add` он в «Changes to be committed» (в индексе).

</details>

**Шаги:**

1. Создай репозиторий и файл:

   ```bash
   mkdir -p ~/git-lab && cd ~/git-lab
   git init
   printf 'GET /healthz\nGET /headers\n' > api.txt
   git status --short
   ```

2. Добавь в индекс, посмотри статус, закоммить:

   ```bash
   git add api.txt
   git status --short
   git commit -m "docs: перечислить ручки API"
   ```

3. Измени файл и сравни области:

   ```bash
   echo 'GET /slow' >> api.txt
   git diff            # рабочий каталог против индекса
   git add api.txt
   git diff --staged   # индекс против последнего коммита
   git commit -m "docs: добавить /slow"
   ```

4. Загляни внутрь коммита:

   ```bash
   git log --oneline
   git cat-file -p HEAD                # объект commit: tree, parent, автор
   ```

**Что должно получиться:**

```text
?? api.txt
A  api.txt
[main (root-commit) 3f2a9c1] docs: перечислить ручки API
 1 file changed, 2 insertions(+)
 create mode 100644 api.txt
```

В `git log --oneline` два коммита с семизначными хешами (у тебя будут другие). В `cat-file -p HEAD` видны строки `tree`, `parent`, `author`, `committer` и сообщение.

**Объясни себе:**

- Почему после второго `git add` команда `git diff` без флагов пустая?
- Чем `git diff --staged` отличается от `git diff`?

**Типичные ошибки:**

- `Author identity unknown` и `*** Please tell me who you are.`: не заданы `user.name` и `user.email`: выполни команды `git config --global` из начала практики.
- `fatal: not a git repository (or any of the parent directories): .git`: ты вне репозитория или забыл `git init`: проверь `pwd`.

### Задание 2. Осмысленная история, ветка и merge

**Цель:** сделать серию понятных коммитов, поработать в ветке и слить её двумя способами.

**Предскажи:** сколько родителей будет у коммита после `git merge`, если `main` за время работы ветки не менялся? А если менялся?

<details markdown="1">
<summary>Ответ</summary>

Если `main` не менялся: слияние fast-forward, нового коммита нет вообще. Если менялся: merge commit с двумя родителями.

</details>

**Шаги:**

1. Ветка `feature/slow`, два коммита:

   ```bash
   cd ~/git-lab
   git switch -c feature/slow
   printf 'slow: ждёт N секунд\n' > slow.txt
   git add slow.txt && git commit -m "feat: описать /slow"
   echo 'предел: 120 секунд' >> slow.txt
   git commit -am "docs: указать предел /slow"
   git log --oneline --graph --all
   ```

2. Вернись в `main` и слей (это fast-forward, `main` не двигался):

   ```bash
   git switch main
   ls
   git merge feature/slow
   git log --oneline --graph
   ```

3. Теперь настоящее расхождение: обе ветки получают коммиты.

   ```bash
   git switch -c feature/error
   echo 'GET /error: всегда 500' > error.txt
   git add error.txt && git commit -m "feat: описать /error"
   git switch main
   echo '# API заметок' > README.md
   git add README.md && git commit -m "docs: добавить README"
   git merge --no-edit feature/error
   git log --oneline --graph
   git branch -d feature/slow feature/error
   ```

**Что должно получиться:**

```text
Updating 8b1e4d2..c7a90ff
Fast-forward
 slow.txt | 2 ++
 1 file changed, 2 insertions(+)
```

После шага 3 в графе видно ромб: строка с `*   ` (merge commit) и две линии, которые сходятся. Merge commit получил сообщение `Merge branch 'feature/error'`.

**Объясни себе:**

- Почему `git branch -d` разрешил удалить ветку сразу после слияния?
- Почему в первом слиянии нет нового коммита, а во втором есть?

**Типичные ошибки:**

- `error: Your local changes to the following files would be overwritten by checkout`: при переключении в рабочем каталоге незакоммиченные правки того же файла: закоммить или отложи `git stash`.
- `error: The branch 'feature/x' is not fully merged`: `-d` защищает от потери неслитых коммитов: сначала слей, либо осознанно удали через `-D`.

### Задание 3. Отмена: restore, revert, reset и спасение из reflog

**Цель:** отработать три вида отмены и вернуть «потерянный» коммит.

**Предскажи:** после `git reset --hard HEAD~1` коммит физически стёрт с диска или его ещё можно достать?

<details markdown="1">
<summary>Ответ</summary>

Можно достать: объект остался в базе, пока его не удалит `git gc`. Найти его поможет `git reflog`.

</details>

**Шаги:**

1. Отмена коммита без переписывания истории:

   ```bash
   cd ~/git-lab
   echo 'мусор' >> api.txt && git restore api.txt   # restore отменяет правку в рабочем каталоге
   echo 'GET /wrong' >> api.txt
   git commit -am "docs: случайная ручка"
   git revert --no-edit HEAD
   git log --oneline -3
   ```

2. Опасный `reset --hard`, затем спасение:

   ```bash
   echo 'GET /important' >> api.txt
   git commit -am "docs: важная ручка"
   git reset --hard HEAD~1     # коммит исчез из log
   git log --oneline -2
   git reflog -5               # находим хеш «важной ручки»
   ```

3. Верни коммит по хешу из reflog (подставь свой; строка вида `HEAD@{1}`):

   ```bash
   git reset --hard 'HEAD@{1}'
   git log --oneline -2
   cat api.txt
   ```

**Что должно получиться:** после `revert` в логе сверху коммит `Revert "docs: случайная ручка"`. После шага 2 в `git log` нет «важной ручки», в `reflog` она есть, после шага 3 вернулась, а в `api.txt` появилась строка `GET /important`.

```text
a4c19e0 (HEAD -> main) docs: важная ручка
5d02b77 Revert "docs: случайная ручка"
```

**Объясни себе:**

- Чем `revert` принципиально отличается от `reset --hard` для истории?
- Что в шаге 3 случилось бы с незакоммиченными правками, если бы они были?

**Типичные ошибки:**

- `error: could not revert 5d02b77... Revert conflict`: правки перекрываются с более поздними: разреши конфликт вручную, затем `git add` и `git revert --continue`.
- `fatal: ambiguous argument 'HEAD@{1}': unknown revision`: в zsh фигурные скобки нужно взять в кавычки, а reflog пуст в новом репозитории: пиши `'HEAD@{1}'` и проверь `git reflog`.

### Задание 4. Поиск сломанного коммита через bisect

**Цель:** найти коммит, который сломал код, за логарифмическое число шагов.

**Предскажи:** сколько проверок понадобится `bisect`, чтобы найти виновного среди 16 коммитов?

<details markdown="1">
<summary>Ответ</summary>

Не больше четырёх (log2 от 16): каждый шаг делит диапазон пополам.

</details>

**Шаги:**

1. Сгенерируй историю из 12 коммитов, где на 8-м «ломается» проверка:

   ```bash
   mkdir -p ~/git-bisect && cd ~/git-bisect && git init -q
   for i in $(seq 1 12); do
     if [ "$i" -ge 8 ]; then echo "broken" > state.txt; else echo "ok" > state.txt; fi
     echo "изменение $i" >> log.txt
     git add . && git commit -q -m "chore: коммит $i"
   done
   git log --oneline | wc -l
   ```

2. Напиши проверку (код выхода 0 = хорошо) и запусти автоматический bisect:

   ```bash
   printf '#!/bin/sh\n[ "$(cat state.txt)" = "ok" ]\n' > check.sh
   chmod +x check.sh
   git bisect start
   git bisect bad HEAD                 # сломано сейчас
   git bisect good HEAD~11             # первый коммит был рабочим
   git bisect run ../git-bisect/check.sh
   git bisect reset
   ```

   Файл `check.sh` не закоммичен, поэтому он не мешает переключению и остаётся на месте.

**Что должно получиться:** в конце вывода `bisect run`:

```text
d41b0c3 is the first bad commit
commit d41b0c3...
    chore: коммит 8
bisect found first bad commit
```

**Объясни себе:**

- Почему скрипту проверки нужен код выхода, а не текст?

**Типичные ошибки:**

- `You need to start by "git bisect start"`: команды `good` и `bad` до `start`: начни с `git bisect start`.
- `bisect run failed: exit code 127 from '...' is < 0 or >= 128`: скрипт не найден или не исполняемый: `chmod +x` и проверь путь.

### Задание 5. Шаг проекта: «Заметки» становятся репозиторием

**Цель:** превратить `~/notes` в git-репозиторий, не закоммитив мусор и секреты.

**Предскажи:** если в `~/notes` есть файл `.env` с секретом, а `.gitignore` создан после `git add .`, попадёт ли `.env` в репозиторий?

<details markdown="1">
<summary>Ответ</summary>

Да, если `git add .` выполнен до создания `.gitignore` (или файл уже был в индексе). `.gitignore` не действует на уже отслеживаемые файлы. Поэтому порядок: сначала `.gitignore`, потом `git add`.

</details>

**Шаги:**

1. Инициализируй репозиторий и создай `.gitignore` до первого `add`:

   ```bash
   cd ~/notes
   git init -b main
   cat > .gitignore <<'EOT'
   .env
   *.log
   __pycache__/
   .venv/
   data/
   EOT
   ```

2. Создай `README.md` проекта:

   ```bash
   cat > README.md <<'EOT'
   # Заметки

   Учебный HTTP-сервис на Python 3.13 без внешних зависимостей.

   ## Запуск

       python3 app.py

   Сервис слушает 127.0.0.1:8080. Проверка: `curl -i http://127.0.0.1:8080/healthz`.

   ## Тесты

       make test
   EOT
   ```

3. Проверь, что будет закоммичено, и убедись, что секретов нет:

   ```bash
   git status --short
   git check-ignore -v .env app.log 2>/dev/null
   git add .
   git status --short
   ```

4. Первый коммит и проверка:

   ```bash
   git commit -m "chore: первая версия проекта Заметки (app v3)"
   git log --oneline
   git ls-files
   ```

**Что должно получиться:** в `git ls-files` есть `app.py`, `test_app.py`, `Makefile`, `README.md`, `.gitignore`, `requirements.txt`, `scripts/` и `deploy/` (то, что уже создано в уроках темы 1 и 2), а `.env`, `*.log` и `data/` нет. Если `.env` есть, `git check-ignore -v .env` печатает правило:

```text
.gitignore:1:.env	.env
```

Состояние проекта после урока: репозиторий `~/notes`, один коммит на `main`, `app.py` версии v3.

**Объясни себе:**

- Почему `.gitignore` создаётся раньше первого `git add`?
- Почему в `.gitignore` стоит `data/`, а не сама база или файл заметок?
- Что ты увидишь в `git status`, если появится новый файл `app.log`?

**Типичные ошибки:**

- `hint: Using 'master' as the name for the initial branch`: не задан `init.defaultBranch`: используй `git init -b main` или переименуй `git branch -M main`.
- `.env` всё равно в `git status` как отслеживаемый: он попал в индекс до `.gitignore`: `git rm --cached .env`, затем коммит (значения в истории при этом остаются, см. ниже).
- `warning: LF will be replaced by CRLF`: сказываются настройки перевода строк в WSL2 при работе в `/mnt/c`: держи проект в домашнем каталоге Linux (`~`), а не в `/mnt/c`.


### Симптом

Сценарий 1: коллега написал: «Сделал `git reset --hard` и пропали два моих коммита с правкой в `app.py`, в `git log` их нет».

Сценарий 2: в истории есть коммит, где закоммичен файл `.env` с настоящим паролем. Репозиторий пока только локальный.

### Гипотезы

1. Коммиты физически удалены, вернуть нельзя, или на них просто ничто не указывает.
2. (Сценарий 2) достаточно добавить `.env` в `.gitignore` или удалить файл новым коммитом.

### Проверки

```bash
git reflog -10                    # где был HEAD до reset
git log --all --oneline -- .env   # в каких коммитах трогали .env
git ls-files | grep '^.env$'      # отслеживается ли сейчас
```

### Исправление

<details markdown="1">
<summary>Разбор сценариев</summary>

**Сценарий 1.** Верна вторая часть гипотезы 1: коммиты остались. Находишь строку в `git reflog` до `reset`, например `HEAD@{1}`, и возвращаешь: `git reset --hard 'HEAD@{1}'` или безопаснее `git branch спасение <хеш>`, чтобы не трогать текущую ветку. Урок: `reset --hard` уничтожает только незакоммиченное, а закоммиченное живёт в reflog.

**Сценарий 2.** Гипотеза 2 неверна: `.gitignore` не действует на отслеживаемые файлы, а удаление новым коммитом оставляет пароль в старых снимках. Порядок реагирования:

1. Ротировать секрет: считай его скомпрометированным (сгенерируй новый через `openssl rand -base64 24` и замени там, где он использовался). Это главное действие.
2. Убрать файл из индекса: `git rm --cached .env`, проверить, что `.env` есть в `.gitignore`.
3. Если история ещё не отправлена, переписать её (например, `git rebase -i` и правка коммита, либо `git filter-repo --path .env --invert-paths`; подробнее про переписывание в [уроке 3.2](02-remotes-workflow.md)). Если уже отправлена в общий репозиторий, чистка истории не отзывает уже скопированное: без шага 1 она бесполезна.
4. Добавить защиту: поиск секретов в CI разбирается в [уроке 3.4](04-quality-security-ci.md).

</details>

## Вопросы с собеседований

### 1. [junior] Ты сделал `git reset --hard HEAD~3` и понял, что сбросил нужное. Что делаешь?

Смотрю `git reflog`: там записан каждый сдвиг `HEAD`. Нахожу хеш состояния до `reset` и делаю `git reset --hard <хеш>` или создаю ветку `git branch rescue <хеш>`. Это работает, пока объекты не удалены сборщиком мусора. Незакоммиченные правки таким способом не вернуть.

**Что хотят услышать:** reflog, ветка для спасения, оговорка про незакоммиченное и локальность reflog.

**Красный флаг:** «всё потеряно, надо писать заново».

### 2. [junior] В чём разница между `git revert` и `git reset`?

`revert` создаёт новый коммит, отменяющий указанный, история не переписывается, поэтому годится для уже отправленных изменений. `reset` двигает ветку назад, коммиты «выпадают», поэтому его применяют только к локальной, никому не отданной работе.

**Что хотят услышать:** историю переписывать нельзя после публикации, режимы soft/mixed/hard.

**Красный флаг:** не различает и советует `reset --hard` для отправленного коммита.

### 3. [junior] Ты закоммитил `.env` с паролем БД, ещё не отправив. Что делаешь?

Первым делом считаю пароль скомпрометированным и меняю его. Потом `git rm --cached .env`, добавляю в `.gitignore`, переписываю историю (`rebase -i` или `filter-repo`), чтобы файла не осталось в снимках. Позже добавляю сканер секретов в CI.

**Что хотят услышать:** ротация секрета раньше чистки истории, `.gitignore` не действует на отслеживаемое.

**Красный флаг:** «удалю файл новым коммитом и всё».

### 4. [junior] Добавил файл в `.gitignore`, а он всё равно отслеживается. Почему?

Потому что файл уже в индексе, а `.gitignore` влияет только на неотслеживаемые. Нужно `git rm --cached файл` и коммит; на диске файл останется.

**Что хотят услышать:** `--cached`, проверка `git check-ignore -v`.

**Красный флаг:** предлагает удалить и создать файл заново.

### 5. [middle] Срочно нужен хотфикс, а у тебя полфайла незакоммиченных правок. Как быть?

`git stash` (можно с `-u` для новых файлов), `git switch -c hotfix main`, чиню, коммичу, возвращаюсь и делаю `git stash pop`. Для чего-то ценного или долгого лучше временный коммит в отдельной ветке: стеш легко забыть.

**Что хотят услышать:** `stash -u`, конфликт при `pop`, альтернатива через WIP-коммит.

**Красный флаг:** «закоммичу всё в main как есть».

### 6. [middle] Тесты позавчера проходили, сегодня падают, между ними 200 коммитов. Как найти виновного?

`git bisect`: отмечаю `bad` для текущего и `good` для позавчерашнего, дальше двоичный поиск примерно за 8 шагов. Лучше автоматически: `git bisect run` со скриптом, где код выхода 0 значит «хорошо». В конце `git bisect reset`.

**Что хотят услышать:** логарифмическое число шагов, `bisect run`, код 125 для «пропустить».

**Красный флаг:** «просмотрю все коммиты по очереди».

### 7. [middle] Что такое detached HEAD и как из него не потерять работу?

`HEAD` указывает на коммит, а не на ветку. Новые коммиты не принадлежат ветке, и после переключения их можно потерять из виду. Если сделал работу, создаю ветку `git switch -c имя` прямо там; если уже ушёл, ищу коммит в `reflog`.

**Что хотят услышать:** связь с reflog, `git switch -c`.

**Красный флаг:** «это ошибка, надо переустановить git».

### 8. [middle] Ты закоммитил в `main`, а надо было в ветку. Коммит не отправлен. Что делаешь?

`git branch feature` (ветка на тот же коммит), затем `git reset --hard HEAD~1` на `main` (или `origin/main`). Если коммит уже отправлен и коллеги на него опираются, `main` не трогаю, а делаю `revert`.

**Что хотят услышать:** новая ветка до `reset`, критерий «отправлено или нет».

**Красный флаг:** копировать файлы руками.

### 9. [middle] Чем fast-forward слияние отличается от merge commit? Когда какое получится?

Fast-forward возможен, если у целевой ветки нет собственных новых коммитов: указатель просто сдвигается, новых коммитов нет. Если ветки разошлись, создаётся merge commit с двумя родителями. Принудительно merge commit даёт `--no-ff`, только fast-forward `--ff-only`.

**Что хотят услышать:** родители, `--ff-only` в скриптах, ромб в `log --graph`.

**Красный флаг:** «merge всегда создаёт коммит».
