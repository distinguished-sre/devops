## Зачем это нужно

Локальный репозиторий из урока 3.1 живёт на одном диске. Как только над кодом работает второй человек (или ты сам с двух машин), появляются вопросы: куда отправлять коммиты, что делать, если `push` отклонён, как разрешить конфликт и почему в `main` нельзя коммитить напрямую. На работе это каждый день: ветка, Pull Request (запрос на слияние), ревью, слияние, чистая история.

Ошибки здесь дорогие: неудачный `force-push` в общую ветку стирает чужие коммиты, а конфликт, разрешённый наспех, ломает прод.

Шаг проекта: «Заметки» уезжают в публичный репозиторий `notes` на GitHub, ветка `main` защищена, изменения идут через Pull Request, первый релизный тег `v0.1.0`.

## Что нужно знать

- [Урок 3.1: Git, коммиты, история и ветки](01-git-basics.md) - коммит, ветка, индекс, `reflog`, `reset` и `revert`; без этого ничего здесь не заработает.
- [Урок 2.2: порты, TCP и SSH](../02-network/02-ports-tcp-ssh.md) - SSH-ключи: GitHub принимает push по SSH так же, как сервер принимает твой вход.

## Теория

### Удалённый репозиторий: remote, origin, upstream

Удалённый репозиторий (remote) это ещё один git-репозиторий, на который твой смотрит по адресу. Имя по умолчанию `origin`: так называется адрес, откуда ты клонировал. Один репозиторий может иметь несколько remote (например, `origin` и `upstream` для форка).

Важно различать три слоя веток:

- локальная ветка `main` (двигаешь ты своими коммитами);
- ветка слежения (remote-tracking branch) `origin/main`: снимок того, что было на сервере при последнем обращении к нему. Ты её сам не двигаешь, её обновляет `git fetch`;
- ветка на самом сервере.

Команды: `git clone` копирует репозиторий целиком; `git fetch` только скачивает новые коммиты и обновляет `origin/*`, ничего не меняя в твоей рабочей ветке; `git pull` это `fetch` плюс слияние (или rebase) в текущую ветку; `git push` отправляет твои коммиты. Связь локальной ветки с удалённой называется upstream: после `git push -u origin main` хватает просто `git push` и `git pull`.

> **Проверь понимание:** ты сделал `git fetch`, а `git log` в твоей ветке не изменился. Это баг?

<details markdown="1">
<summary>Ответ</summary>

Нет. `fetch` обновляет только `origin/main`, но не твою `main`. Посмотреть, что пришло: `git log main..origin/main`. Чтобы принять изменения, нужны `merge` или `rebase`. Поэтому `fetch` безопасен в любой момент, а `pull` уже меняет твою ветку.

</details>

### Merge и rebase: два способа собрать историю

Ты и коллега ответвились от одного коммита и оба сделали по коммиту. Истории разошлись. Есть два пути.

`git merge origin/main` создаёт коммит слияния (merge commit) с двумя родителями. История честная, но в ней появляются «ёлочки» из служебных коммитов.

`git rebase origin/main` берёт твои коммиты, временно откладывает и проигрывает их заново поверх `origin/main`. История линейная. Но у переигранных коммитов **новые хеши**: git создаёт копии, а не двигает старые.

Отсюда золотое правило: **не делай rebase коммитов, которые уже отправлены и на которых основана чужая работа**. Свою личную ветку переписывать можно, общую `main` нельзя.

Практическое правило команды: перед Pull Request подтяни свежий `main` в свою ветку через rebase, а в `main` влей PR через squash или merge (это настройка репозитория).

> **Проверь понимание:** почему после `rebase` обычный `git push` отклоняется, если ветку уже отправляли раньше?

<details markdown="1">
<summary>Ответ</summary>

Коммиты после rebase получили новые хеши, а на сервере лежат старые. Для сервера ветки разошлись, простое добавление невозможно (non-fast-forward). Нужен `git push --force-with-lease`, и только для своей личной ветки.

</details>

### Конфликты и маркеры

Конфликт (conflict) возникает, когда две ветки изменили одни и те же строки и git не может выбрать сам. Он останавливается и пишет в файл маркеры:

```text
<<<<<<< HEAD
version=1.5
=======
version=2.0
>>>>>>> feature
```

Между `<<<<<<<` и `=======` версия «текущей стороны», между `=======` и `>>>>>>>` версия «приходящей». Ты редактируешь файл так, как должно быть в итоге, **удаляешь все три строки маркеров**, делаешь `git add файл`, затем продолжаешь: `git rebase --continue` или `git commit` для merge. Отменить всё и вернуться: `git rebase --abort` или `git merge --abort`.

Внимание: в `rebase` стороны «наоборот». `HEAD` это то, что уже лежит на `origin/main` (плюс уже переигранные коммиты), а «приходящая» сторона это твой коммит, который сейчас проигрывается. Не путай при выборе.

> **Проверь понимание:** конфликт разрешён, файл сохранён. Что ещё обязательно сделать до `rebase --continue`?

<details markdown="1">
<summary>Ответ</summary>

`git add <файл>`. Пока файл не добавлен в индекс, git считает конфликт неразрешённым (`git status` покажет `both modified`). Ещё стоит запустить тесты: разрешение без проверки часто даёт код, который выглядит целым, но ведёт себя неверно.

</details>

### Интерактивный rebase и force-with-lease

`git rebase -i HEAD~4` открывает список последних четырёх коммитов в редакторе. Перед каждым слово-команда: `pick` (оставить), `reword` (поменять сообщение), `squash` (слить с предыдущим и объединить сообщения), `fixup` (слить, сообщение выбросить), `drop` (удалить). Порядок строк можно менять. Так превращают «wip», «fix typo», «ещё fix» в один осмысленный коммит до отправки на ревью.

После переписывания отправленной ветки нужен `force`. Голый `--force` затирает всё на сервере. Безопаснее `git push --force-with-lease`: он проверяет, что удалённая ветка всё ещё указывает туда, где ты видел её в последний раз (`origin/feature`). Если коллега успел добавить коммит, push будет отклонён с сообщением `stale info`, и ты его не сотрёшь.

`git cherry-pick <хеш>` копирует один коммит в текущую ветку. Типичный случай: исправление из `main` нужно перенести в релизную ветку.

> **Проверь понимание:** чем `--force-with-lease` лучше `--force`, и в каком случае он всё равно опасен?

<details markdown="1">
<summary>Ответ</summary>

`--force-with-lease` не затрёт коммиты, которых ты ещё не видел. Но если ты сделал `git fetch` и не посмотрел, что пришло, «аренда» уже обновлена, и чужие коммиты всё равно исчезнут. Плюс он не спасает общие ветки: force в `main` запрещают защитой ветки.

</details>

### Pull Request, ревью и защита main

Pull Request (PR) это предложение влить ветку в другую, вокруг которого строится процесс: обсуждение, комментарии к строкам, проверки (в 3.3 добавим автотесты), одобрение. Модель называется GitHub Flow: `main` всегда рабочая, каждое изменение живёт в короткой ветке и попадает в `main` только через PR. Ей родственен trunk-based development: ветки живут часами, а незаконченное прячется за флагами функций (feature flags). GitFlow с долгоживущими `develop` и `release/*` тяжелее и подходит для версионных продуктов, но не для сервисов, которые выкатываются постоянно.

Хороший PR: одна цель, до 300-400 строк диффа, описание «что и зачем», ссылка на задачу, ответ «как проверил».

Способы слияния: merge commit (сохраняет все коммиты ветки и добавляет коммит слияния), squash (вся ветка в один коммит в `main`, самая чистая история) и rebase-merge (коммиты ветки переигрываются в `main` линейно).

Защита ветки (branch protection или ruleset): запрет прямого push, запрет force-push и удаления, обязательный PR, обязательные проверки и ревью. Файл `CODEOWNERS` назначает владельцев путей: PR, затрагивающий `/deploy/`, автоматически просит ревью у команды платформы. Защита работает в публичных репозиториях бесплатного плана, поэтому репозиторий проекта публичный.

> **Проверь понимание:** ты единственный владелец репозитория и включил обязательное одобрение одним ревьюером. Что произойдёт при попытке слить свой PR?

<details markdown="1">
<summary>Ответ</summary>

Автор не может одобрить собственный PR, кнопка слияния будет заблокирована. Для соло-режима ставят 0 обязательных одобрений (но оставляют требование PR) или разрешают администратору обойти правило. В команде так делать нельзя: ревью обязательно.

</details>

### Теги и семантические версии

Тег (tag) это неподвижная метка на коммите. Аннотированный тег (`git tag -a`) хранит автора, дату и сообщение, он подходит для релизов. Семантическая версия (semver) имеет вид `MAJOR.MINOR.PATCH`: ломающее изменение, новая совместимая функция, исправление. Версия `0.x.y` означает «API ещё не стабилен». Теги не отправляются автоматически: `git push` их не берёт, нужен `git push origin v0.1.0`. Оформление релизов и автоматизация разбираются в уроке 3.5.

> **Проверь понимание:** почему тег нельзя «передвинуть» так же просто, как ветку, и почему это хорошо?

<details markdown="1">
<summary>Ответ</summary>

Ветка двигается с каждым коммитом, тег остаётся на одном коммите. Это гарантирует, что `v0.1.0` всегда означает один и тот же код, на него можно сослаться в релизе, образе или отчёте о баге. Перемещённый тег (`git tag -f`) ломает это обещание, поэтому в общем репозитории так не делают.

</details>

## Практика

Первые три задания идут в песочнице без GitHub: роль сервера играет «голый» репозиторий (bare repository, без рабочих файлов) в каталоге на диске, а «коллегой» служит второй клон. Так можно безопасно ломать. Последнее задание работает с настоящим GitHub.

Подготовка (один раз):

```bash
# имя и почта для коммитов (подставь свои)
git config --global user.name "Твоё Имя"
git config --global user.email "you@example.com"
# новые репозитории создаются с веткой main
git config --global init.defaultBranch main
# pull без слияния истории запрещён: при расхождении стратегию выбираешь сам
git config --global pull.ff only
git --version
```

### Задание 1. Свой сервер, два клона и разница fetch и pull

**Цель:** создать общий репозиторий, подключить два рабочих каталога (ты и «коллега») и увидеть, что делает `fetch`.

**Предскажи:** ты сделал коммит в клоне `alice` и `push`. В клоне `bob` выполнил `git fetch`. Изменятся ли файлы в каталоге `bob`? Что покажет `git status`?

<details markdown="1">
<summary>Ответ</summary>

Файлы не изменятся. `git status -sb` покажет `[behind 1]`: новый коммит уже в `origin/main`, но локальная `main` не сдвинулась. Файлы поменяются только после `git pull` (или `merge`/`rebase`).

</details>

**Шаги:**

1. Создай общий репозиторий и первый клон:

```bash
mkdir -p ~/sandbox && cd ~/sandbox
# «сервер»: голый репозиторий
git init --bare -b main origin.git
# клон Алисы (это ты)
git clone origin.git alice
cd alice
printf 'app=notes\nversion=1.0\nowner=alice\n' > config.txt
git add config.txt
git commit -m "Добавить config.txt"
git push -u origin main
git remote -v
```

2. Клон коллеги и коммит Алисы:

```bash
cd ~/sandbox
git clone origin.git bob
cd alice
echo 'debug=false' >> config.txt
git commit -am "Добавить debug"
git push
```

3. В каталоге Боба посмотри, что видно до и после `fetch`:

```bash
cd ~/sandbox/bob
git status -sb
git fetch
git status -sb
git log --oneline main..origin/main
git pull
git log --oneline
```

**Что должно получиться:**

```text
## main...origin/main
## main...origin/main [behind 1]
a3f9c21 Добавить debug
Updating 7be0d14..a3f9c21
Fast-forward
 config.txt | 1 +
 1 file changed, 1 insertion(+)
a3f9c21 (HEAD -> main, origin/main, origin/HEAD) Добавить debug
7be0d14 Добавить config.txt
```

Хеши у тебя будут другими.

**Объясни себе:**
- Почему до `fetch` статус не знал про новый коммит?
- Что означает `Fast-forward` и почему тут не было слияния?
- Чем `origin/main` отличается от `main` в каталоге `bob`?

**Типичные ошибки:**
- `fatal: repository 'origin.git' does not exist`: ты не в каталоге `~/sandbox` или опечатка в пути: проверь `pwd` и `ls`.
- `Author identity unknown`: не настроены `user.name` и `user.email`: выполни блок подготовки.
- `fatal: Not possible to fast-forward, aborting.`: у тебя в `bob` уже есть свой коммит, а на сервере другой, то есть ветки разошлись: это тема следующего задания, а здесь коммитить в `bob` рано.

### Задание 2. Rejected non-fast-forward и конфликт при rebase

**Цель:** воспроизвести самую частую ошибку командной работы и решить её без потери чужих коммитов.

**Предскажи:** Алиса и Боб оба изменили строку `version=` в `config.txt` на разные значения. Алиса запушила первой. Что случится у Боба на `git push`? А на `git pull --rebase`?

<details markdown="1">
<summary>Ответ</summary>

Push Боба будет отклонён (`rejected ... fetch first`): на сервере есть коммит, которого у него нет. `git pull --rebase` попытается переиграть коммит Боба поверх коммита Алисы, наткнётся на одну и ту же строку и остановится на конфликте.

</details>

**Шаги:**

1. Алиса меняет версию и отправляет (на macOS `sed -i ''` вместо `sed -i`):

```bash
cd ~/sandbox/alice
sed -i 's/version=1.0/version=2.0/' config.txt
git commit -am "Поднять версию до 2.0"
git push
```

2. Боб, не подтянув изменения, делает свой коммит в той же строке:

```bash
cd ~/sandbox/bob
sed -i 's/version=1.0/version=1.5/' config.txt
git commit -am "Поднять версию до 1.5"
git push
```

3. Прочитай ошибку и подтяни чужую работу через rebase:

```bash
git pull --rebase
git status
cat config.txt
```

4. Разреши конфликт: открой `config.txt`, оставь одну строку `version=2.0` (условно договорились, что верна версия Алисы), удали все маркеры, затем:

```bash
git add config.txt
git rebase --continue
git log --oneline --graph
git push
```

Если запутался: `git rebase --abort` вернёт всё как было до `pull`.

**Что должно получиться:**

```text
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '/home/you/sandbox/origin.git'
hint: Updates were rejected because the remote contains work that you do not
hint: have locally.
```

После `pull --rebase`:

```text
CONFLICT (content): Merge conflict in config.txt
error: could not apply 5c1d8e2... Поднять версию до 1.5
```

Итог `git log --oneline --graph`: линейная история, коммит Боба лежит выше коммита Алисы, слияний нет.

**Объясни себе:**
- Почему сервер отклонил push, хотя код Боба «правильный»?
- Почему после rebase хеш коммита Боба стал другим?
- Что было бы, если бы Боб сделал `git push --force`?

**Типичные ошибки:**
- `error: Pulling is not possible because you have unmerged files.`: конфликт не разрешён или забыт `git add`: смотри `git status`.
- В файле остались строки `<<<<<<< HEAD`: маркеры не удалены: найди их командой `grep -n '^<<<<<<<\|^=======\|^>>>>>>>' config.txt`.
- `fatal: It seems that there is already a rebase-merge directory`: предыдущий rebase не закончен: выполни `git rebase --continue` или `git rebase --abort`.

### Задание 3. Чистим историю через rebase -i

**Цель:** склеить четыре черновых коммита в два осмысленных и безопасно отправить переписанную ветку.

**Предскажи:** после `rebase -i` ты сделал `git push`, а ветка уже была на сервере. Отправится ли она? Почему?

<details markdown="1">
<summary>Ответ</summary>

Нет. Хеши коммитов изменились, ветка на сервере и локальная разошлись, будет `rejected (non-fast-forward)`. Нужен `git push --force-with-lease`.

</details>

**Шаги:**

1. Создай личную ветку с четырьмя черновыми коммитами и отправь её:

```bash
cd ~/sandbox/alice
git switch -c feature/logging
echo 'log_level=info' >> config.txt
git commit -am "wip: добавить логирование"
echo 'log_file=/var/log/notes.log' >> config.txt
git commit -am "wip: путь к логу"
echo 'retention=7' >> config.txt
git commit -am "Добавить срок хранения"
sed -i 's/retention=7/retention=14/' config.txt
git commit -am "fix: срок хранения 14 дней"
git push -u origin feature/logging
git log --oneline
```

2. Запусти интерактивный rebase на 4 коммита:

```bash
git rebase -i HEAD~4
```

3. В открывшемся редакторе строки идут от старых к новым. Приведи первые слова к такому виду (хеши свои):

```text
pick 1a2b3c4 wip: добавить логирование
squash 5d6e7f8 wip: путь к логу
pick 9a0b1c2 Добавить срок хранения
fixup 3d4e5f6 fix: срок хранения 14 дней
```

Сохрани. Для первой пары git откроет редактор сообщения: оставь одну строку `Добавить логирование в config.txt`.

4. Проверь результат и отправь:

```bash
git log --oneline
git push
git push --force-with-lease
```

**Что должно получиться:**

```text
b7c8d9e Добавить срок хранения
4f5a6b7 Добавить логирование в config.txt
a3f9c21 Поднять версию до 2.0
```

Первый `git push` отклонён (`non-fast-forward`), второй проходит.

**Объясни себе:**
- Чем `squash` отличается от `fixup`?
- Почему тут `--force-with-lease` допустим, а в `main` нет?
- Что произойдёт с коммитом коллеги, если он успел запушить в `feature/logging` между твоим `fetch` и push?

**Типичные ошибки:**
- `error: cannot 'squash' without a previous commit`: `squash` стоит первой строкой списка: первой должна быть `pick`.
- Коммиты пропали после rebase: строки в редакторе случайно стали `drop`: найди прежнее состояние в `git reflog` и вернись `git reset --hard HEAD@{N}` (см. урок 3.1).
- `! [rejected] feature/logging -> feature/logging (stale info)`: на сервере появились чужие коммиты: сделай `git fetch`, посмотри `git log origin/feature/logging` и реши, что делать.

### Задание 4. Проект «Заметки» на GitHub: PR, защита main, тег v0.1.0

**Цель:** отправить проект `~/notes` в публичный репозиторий, защитить `main` и пройти полный цикл: ветка, Pull Request, ревью, squash, тег.

**Предскажи:** после включения защиты ветки ты выполнил `git push origin main` с новым коммитом. Что ответит GitHub?

<details markdown="1">
<summary>Ответ</summary>

Push будет отклонён: `remote: error: GH013: Repository rule violations found`, с текстом про обязательный Pull Request. Это правильное поведение: `main` меняется только через PR.

</details>

**Шаги:**

1. Создай SSH-ключ для GitHub и добавь публичную часть на странице GitHub: Settings, SSH and GPG keys, New SSH key. Ключи устроены так же, как в уроке 2.2:

```bash
ssh-keygen -t ed25519 -C "notes-github" -f ~/.ssh/id_ed25519_github
cat ~/.ssh/id_ed25519_github.pub
```

Вставь вывод последней команды в форму на GitHub. Затем укажи SSH, какой ключ использовать для GitHub:

```bash
cat >> ~/.ssh/config <<'CFG'

  IdentityFile ~/.ssh/id_ed25519_github
  IdentitiesOnly yes

ssh -T git@github.com
```

2. На GitHub создай **публичный** репозиторий `notes` (New repository, без README, без .gitignore, без лицензии). Подключи и отправь:

```bash

git status -sb
git remote add origin git@github.com:<твой-логин>/notes.git
git branch -M main
git push -u origin main
```

3. Включи защиту `main`: Settings, Rules, Rulesets, New branch ruleset. Target: Default branch. Отметь: Restrict deletions, Require a pull request before merging (Required approvals: 0, так как ты один), Block force pushes. Enforcement: Active. В Settings, General, Pull Requests оставь только Allow squash merging и включи Automatically delete head branches.

4. Проверь защиту:

```bash
echo "" >> README.md
git commit -am "Проверка защиты"
git push origin main
git reset --hard HEAD~1
```

5. Проведи изменение через PR. Добавь в проект описание процесса:

```bash
git switch -c docs/contributing
cat > CONTRIBUTING.md <<'MD'

1. Создай ветку от актуального main: `git switch -c fix/короткое-имя`.
2. Делай небольшие коммиты, перед PR склей черновые через `git rebase -i`.
3. Открой Pull Request, опиши что и зачем изменено и как проверено.
4. В main изменения попадают только через squash-merge.

```

6. Открой Pull Request на странице репозитория (кнопка Compare & pull request). В описании напиши, что изменено. Перейди на вкладку Files changed, оставь себе комментарий к строке 4 (например: «Уточнить, как именно проверять») и ответь на него. Нажми Squash and merge.

7. Верни изменения на компьютер и поставь тег:

```bash
git switch main
git pull
git branch -D docs/contributing
git tag -a v0.1.0 -m "Первый релиз: app v3, процесс через Pull Request"
git push origin v0.1.0
git log --oneline --decorate -3
git ls-remote --tags origin
```

**Что должно получиться:**

```text

```

Попытка push в защищённую `main`:

```text

remote: - Changes must be made through a pull request.

```

Итог:

```text

9f8e7d6 Добавить README проекта
2b3c4d5 Добавить .gitignore
```

`main` получила один squash-коммит с номером PR `(#1)`, тег `v0.1.0` виден и локально, и на сервере (`git ls-remote` печатает хеш и `refs/tags/v0.1.0`). Состояние проекта после урока: публичный репозиторий `notes`, защищённая `main`, PR-процесс, тег `v0.1.0`, `app.py` версии v3.

**Объясни себе:**
- Зачем в ruleset включён запрет force-push, если ты работаешь один?
- Почему после squash-merge локальную ветку приходится удалять с `-D`, а не `-d`?
- Чем аннотированный тег лучше лёгкого для релиза?

**Типичные ошибки:**
- `git@github.com: Permission denied (publickey).`: GitHub не знает ключ или SSH берёт не тот: проверь `ssh -vT git@github.com`, блок `Host github.com` в `~/.ssh/config` и что вставлен именно `.pub`.
- `error: remote origin already exists.`: remote уже добавлен: поправь адрес командой `git remote set-url origin git@github.com:<логин>/notes.git`.
- `error: src refspec main does not match any`: локальная ветка называется иначе (например `master`) или нет коммитов: выполни `git branch -M main` и проверь `git log`.
- Кнопка Squash and merge неактивна: ruleset требует больше 0 одобрений или проверки, которых пока нет: поставь Required approvals: 0.
- `error: The branch 'docs/contributing' is not fully merged.`: squash создал на `main` новый коммит, git не видит ветку влитой: после проверки на GitHub удали ветку через `-D`.
- `! [rejected] v0.1.0 -> v0.1.0 (already exists)`: такой тег уже есть на сервере: не двигай его, создай следующую версию.

## Сломай и почини

Запусти сценарий (скрипт читать не нужно, разбирай симптом как на настоящем инциденте):

```bash
cd ~/notes/break/3.2 && ./break.sh random
```

Или выбери номер: `./break.sh 1`, `./break.sh 2` или `./break.sh 3`.

### Симптом

Сценарий оставляет песочницу в одном из состояний: `push` отвечает `rejected`, `rebase` остановился посреди операции, или общая ветка на сервере потеряла коммиты после чьего-то `push --force`. Твоя задача: понять, что произошло, не потеряв ничью работу.

### Гипотезы

1. Ветки разошлись: на сервере есть коммиты, которых нет у тебя.
2. Git остановился на конфликте и ждёт твоего решения.
3. Кто-то переписал историю общей ветки: `origin/*` указывает не туда, куда твоя ветка.
4. Проблема в доступе к серверу (проверять последней).

### Проверки

```bash
git status                            # rebase in progress, ahead/behind, both modified
git fetch --all --prune               # обновить представление о сервере
git log --oneline --graph --all -15   # где разошлись ветки
git diff --name-only --diff-filter=U  # список неразрешённых файлов
git reflog -15                        # что было с твоей веткой раньше
git log origin/main..main             # мои коммиты, которых нет на сервере
git log main..origin/main             # чужие коммиты, которых нет у меня
```

### Исправление

<details markdown="1">
<summary>Разбор сценариев</summary>

**1. `rejected: non-fast-forward`.** Проверки показывают, что `main..origin/main` не пуст. Лечение: `git pull --rebase` (или `git fetch` и `git rebase origin/main`), при необходимости разреши конфликты, запусти тесты, затем обычный `git push`. Force не нужен и вреден: он стёр бы чужие коммиты.

**2. Конфликт при rebase.** `git status` показывает `rebase in progress` и файлы `both modified`. Открой файл, оставь итоговый вариант, удали маркеры (`grep -n '^<<<<<<<\|^=======\|^>>>>>>>'` не должен ничего находить), `git add файл`, `git rebase --continue`. Если решение неочевидно: `git rebase --abort`, поговори с автором второго изменения и повтори.

**3. Force-push в общую ветку.** Чужие коммиты пропали с сервера. Найти потерянное: у того, кто делал `fetch` до force-push, коммиты живут в `git reflog` (запись вида `origin/main@{1}`). Восстановление: `git branch rescue <хеш>`, затем согласованный `git push origin rescue:main --force-with-lease` или отдельная ветка на сервере. Как правильно: защитить `main` (запрет force-push), в личных ветках использовать только `--force-with-lease`, а ошибочное изменение в общей ветке откатывать через `git revert`, который добавляет новый коммит, а не переписывает историю.

</details>

## Вопросы с собеседований

### 1. [junior] Твой `git push` отклонён с `rejected non-fast-forward`. Что делаешь?

Читаю сообщение: на сервере есть коммиты, которых нет у меня. Делаю `git fetch`, смотрю `git log main..origin/main`, затем `git pull --rebase` или merge, разрешаю конфликты, запускаю тесты и пушу. `--force` не использую.

**Что хотят услышать:** понимание причины (ветки разошлись), `fetch` перед решением, отказ от force в общей ветке, тесты после разрешения.

**Красный флаг:** «просто делаю `git push -f`».

### 2. [junior] Чем `git fetch` отличается от `git pull`?

`fetch` скачивает коммиты и обновляет `origin/*`, не трогая мою ветку. `pull` это `fetch` плюс `merge` (или `rebase` с `--rebase`). Я предпочитаю сначала `fetch` и посмотреть, что пришло.

**Что хотят услышать:** ветка слежения `origin/main`, безопасность `fetch`, что `pull` может создать merge commit или конфликт.

**Красный флаг:** «`pull` скачивает, `fetch` тоже скачивает, разницы нет».

### 3. [middle] Прод отвечает 502 после вчерашнего мержа в `main`. Как через git найти, что изменилось, и откатить?

Смотрю `git log --oneline --since=yesterday` и `git diff <прошлый-тег>..HEAD`, если версии размечены тегами. Подозрительный коммит проверяю через `git bisect` или `git show`. Откат делаю через `git revert <хеш>` в новом PR (в защищённой `main` иначе нельзя), а не через `reset`. Параллельно возвращаю сервис на предыдущий тег.

**Что хотят услышать:** `revert` вместо переписывания истории общей ветки, теги как точки отката, PR даже для срочного отката, разбор причины после восстановления.

**Красный флаг:** «сделаю `git reset --hard` и `push --force` в main».

### 4. [middle] Коллега сделал `git push --force` в `main`, и вчерашние коммиты пропали. Что делаешь?

Не паникую: у меня в `reflog` и в `origin/main@{1}` остались хеши. Создаю ветку `git branch rescue <хеш>`, сообщаю команде, что произошло, и вместе восстанавливаем `main` после согласования. Потом включаю защиту ветки, запрещающую force-push.

**Что хотят услышать:** `reflog`, ветка-спасатель до любых других действий, коммуникация, защита `main` как системное решение, а не поиск виноватого.

**Красный флаг:** «пишу заново по памяти» или «сам force-push'ну свою версию, кто успел, тот и прав».

### 5. [middle] Когда rebase делать нельзя?

Нельзя переписывать историю коммитов, которые уже лежат в общей ветке или на которых основана чужая работа: у переигранных коммитов другие хеши, и у коллег ветки разойдутся с сервером. Свою личную ветку до слияния переписывать можно и нужно, с `--force-with-lease`.

**Что хотят услышать:** «новые хеши», различие общей и личной ветки, `force-with-lease`.

**Красный флаг:** «rebase всегда лучше merge» или «rebase никогда нельзя».

### 6. [junior] Во время `rebase` появился конфликт. Как решаешь?

`git status` покажет файлы `both modified`. Открываю файл, оставляю верный итог (при необходимости спрашиваю автора второго изменения), удаляю маркеры, `git add`, `git rebase --continue`. Если запутался, `git rebase --abort`. В конце запускаю тесты.

**Что хотят услышать:** маркеры, `add` и `continue`, `abort` как страховка, тесты, вопрос автору.

**Красный флаг:** «принимаю свою версию целиком, чтобы быстрее».

### 7. [middle] Что делает `--force-with-lease` и почему лучше `--force`?

Он отправляет форс только если удалённая ветка всё ещё там, где я её видел в последний раз. Если коллега добавил коммит, push отклонится (`stale info`). Ограничение: если я сделал `fetch` и не посмотрел, что пришло, защита уже не сработает.

**Что хотят услышать:** проверка «ожидаемого» значения, применимость только к личным веткам, что это не замена защите main.

**Красный флаг:** «это то же самое, только длиннее».

### 8. [junior] Как сделать так, чтобы в `main` нельзя было пушить напрямую?

Включаю правило защиты ветки (branch protection или ruleset): обязательный Pull Request, запрет force-push и удаления, обязательные проверки (после появления CI) и ревью. Для критичных путей добавляю `CODEOWNERS`.

**Что хотят услышать:** PR, ревью, статус-проверки, запрет force-push, `CODEOWNERS`, вопрос об исключениях для администраторов.

**Красный флаг:** «договоримся в команде не пушить в main».

### 9. [middle] Чем squash-merge отличается от merge commit, и что выберешь для команды?

Squash сворачивает ветку в один коммит: `main` чистая, откат целой функции одним `revert`, но теряется детальная история внутри ветки. Merge commit сохраняет всё, но засоряет `main`. Для сервиса с короткими ветками выбираю squash и хорошие заголовки PR.

**Что хотят услышать:** плюсы и минусы обоих, связь с размером PR, влияние на `git bisect` и `revert`.

**Красный флаг:** «разницы нет, история одна и та же».

### 10. [middle] Срочное исправление уже есть в `main`, а нужно и в релизной ветке `release/1.2`. Как перенесёшь?

Через `git cherry-pick -x <хеш>` в ветке от `release/1.2` и отдельный PR. Для squash в `main` хеш один. Проверяю, что исправление не зависит от изменений, которых нет в релизной ветке.

**Что хотят услышать:** `cherry-pick`, PR даже в релизную ветку, риск скрытых зависимостей, `-x` для записи исходного хеша.

**Красный флаг:** «сливаю весь `main` в релизную ветку».

### 11. [middle] Команда спорит: GitHub Flow, trunk-based или GitFlow. Что предложишь для сервиса, который выкатывается каждый день?

Trunk-based или GitHub Flow: короткие ветки, частые PR, `main` всегда готова к выкатке, незаконченное скрывается за флагами. GitFlow с `develop` и `release/*` оправдан для версионных продуктов с поддержкой нескольких версий сразу.

**Что хотят услышать:** связь стратегии с частотой релизов, размер ветки, feature flags, автотесты как условие.

**Красный флаг:** «GitFlow, потому что он самый полный».

### 12. [junior] Что такое семантическая версия и как в git отмечают релиз?

`MAJOR.MINOR.PATCH`: ломающее изменение, совместимая функция, исправление. Релиз отмечают аннотированным тегом `git tag -a v0.1.0 -m "..."` и отправляют его `git push origin v0.1.0`. Тег не двигают.

**Что хотят услышать:** смысл частей номера, что теги не пушатся автоматически, неизменность тега.

**Красный флаг:** «версия это просто ветка, которую я назвал `v1`».
